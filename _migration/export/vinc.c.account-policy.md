# 계정 정책 — 개인·팀 티어, 도메인 한도, 팀 협업, 결제

> **DEC AP-1 — 채택(발주자 결정 2026-08-02).** 계정 체계를 **개인(Free·Pro)과 팀**으로
> 가르고, 개인 Free 의 MCP 호출 한도를 Pro 급으로 올리는 대신 **주제(domain) 개수**를
> 차별축으로 삼으며, **팀**(상위 계정이 이메일로 초대·공유 그래프 공동 작업·멤버별 권한,
> 유료 전용)을 신설한다. 대금 수납은 **Paddle(MoR) 단독**으로 시작하고 국내 매출 성장 시
> Toss Payments 를 국내 경로로 추가한다.
>
> 이 문서는 **as-built 가 아니라 설계 정본**이다. §9 롤아웃(P0~P4)이 구현 세션의 지침이며,
> 각 단계가 착지할 때마다 §12 장부에 결과를 남긴다. 구현이 설계와 어긋나면 **코드가 아니라
> 이 문서를 먼저 고친다**(SSoT 원칙).
>
> [[vinc.c.web-vincs-app]] 이 계정·웹 표면의 as-built 이고, 스키마 정본은
> `Vinc/emails/ARCHITECTURE.md`(§4 테이블 DDL)이다. 이 문서는 그 위에 **정책 델타**를
> 얹는다 — 기존 서술을 재기재하지 않고 `#§N` 으로 참조한다.

## 1. 결정과 범위

### 1.1 확정된 결정 (발주자, 2026-08-02)

| # | 항목 | 결정 |
|---|---|---|
| AP-1a | 상위 구분 | **개인**(Free·Pro) / **팀**(유료 전용) 2계층 |
| AP-1b | 개인 Free 의 MCP 호출 한도 | **현 Pro 급으로 상향**(일 2,000회). 무료 15회/일 폐기 |
| AP-1c | 개인 Free 의 차별축 | **주제(domain) 5개**. 초과 시 신규 주제 생성만 차단 |
| AP-1d | 개인 Pro | 주제 무제한. **월 ₩9,900 · 연 ₩99,000** |
| AP-1e | 팀 | 시트당 **월 ₩15,000 · 연 ₩144,000**. 무료 등급 없음 |
| AP-1f | 결제 | **Paddle(MoR) 단독 시작** → 국내 성장 시 Toss 추가(§7) |
| AP-1g | 팀 v1 표면 | **웹 우선**. 데스크탑의 팀 그래프 동기화는 후속(§4.7) |

### 1.2 왜 주제 개수인가

노션의 무료 플랜은 **혼자 쓰는 워크스페이스의 블록 수를 제한하지 않는다**(1,000블록
상한은 멤버가 2명 이상일 때만 걸린다). 과금 트리거를 협업·파일 무게·이력 보존으로
옮겨두고, 솔로 사용자는 끝까지 무료로 쓰게 두는 구조다 — 무료 등급을 체험판이 아니라
획득 채널로 쓰는 설계다(부록 A).

Vinc 도 같은 형태를 취한다. 호출 한도를 조이면 **도구가 도구로서 못 쓰이게 되어**
제품을 판단할 기회 자체가 사라진다. 대신 **주제 개수**를 축으로 삼는다:

- 혼자 한 가지 일(업무 하나·연구 하나)에 쓰는 사용자는 5개 안에서 영구히 무료다.
- 여러 갈래를 한 그래프에 모으기 시작하는 순간이 곧 제품 가치를 느낀 순간이고,
  그때 Pro 전환 동기가 자연 발생한다.
- 주제는 **자유 문자열**(§3.1)이라 사용자가 의미를 정하고, 강제 분류가 아니다.

### 1.3 티어 정의

| | 개인 Free | 개인 Pro | 팀 |
|---|---|---|---|
| 가격 | ₩0 | 월 ₩9,900 · 연 ₩99,000 | 시트당 월 ₩15,000 · 연 ₩144,000 |
| MCP 도구 호출 | 일 2,000회 | 일 2,000회 | 일 2,000회(멤버별) |
| 주제 개수 | **5개** | 무제한 | 무제한 |
| 호스티드 그래프 | 1개(개인) | 1개(개인) | 개인 1 + **팀 공유 1** |
| 웹 Vinc·데스크탑·동기화 | ○ | ○ | ○(팀 그래프는 웹 우선) |
| 멤버 초대·권한 | X | X | **○**(열람자·편집자·관리자) |

호출 한도가 세 등급 모두 같은 것은 의도다(AP-1b). 한도 수치는 코드 상수가 아니라
환경변수이므로(§3.4) 운영 중 조정 가능하다.

### 1.4 범위 밖

- **그래프 엔진 스키마 변경 없음.** 팀은 소유자 문자열 하나로 성립한다(§4.1).
- **주제별·노드별 세밀 권한 없음.** v1 권한은 **작업 종류(op) 단위**다(§4.4).
  주제 단위 ACL 은 전 질의 플랜에 술어를 심어야 해서 별건이다.
- **저작자 기록 없음.** 팀 그래프의 노드에 "누가 썼는가"가 남지 않는다(§4.6).
- **데스크탑의 팀 그래프 동기화 없음**(v1). 제약과 해소 경로는 §4.7.
- **카드 정보 보관 없음.** 결제수단은 전량 결제사가 보유한다(PCI SAQ-A 유지,
  `Vinc/emails/ARCHITECTURE.md#§4.5`).

## 2. 플랜 체계와 자격 판정

### 2.1 진실원천과 투영

```
subscriptions(구독 실체)  ──투영──▶  users.plan('free'|'pro')  ──▶ 세션·API키·어서션
        │                                    ▲
        │                              billing 서비스가 유일 작성자
        └── team_members × teams ──▶ 팀 자격(관계형 판정, users.plan 미기록)
```

- **`subscriptions` 가 진실원천이다.** 결제사 웹훅이 이 표를 갱신한다.
- **`users.plan` 은 투영 캐시다.** billing 서비스만 쓴다(다른 코드의 쓰기 금지 — 불변식).
  세션 적재가 매 요청 `users` 를 조인하므로(`account/src/repos/sessions.ts`), 투영만
  갱신하면 **기존 판독처 5곳이 코드 변경 없이** 올바른 값을 본다:
  `types.ts`(AuthUser) · `repos/sessions.ts` · `repos/apiKeys.ts` · `routes/me.ts` ·
  `routes/connect.ts`(승인 어서션 서명) · `routes/internal.ts`(verify-key 응답).
- **팀 자격은 `users.plan` 에 절대 넣지 않는다.** 팀은 사용자 속성이 아니라
  **관계**(어느 팀에 어떤 역할로 속하는가)이고, 한 사람이 개인 Pro 이면서 동시에
  팀 편집자일 수 있다. 두 축은 직교한다.
- DB 열거형 `users.plan ENUM('free','pro')` 는 **바꾸지 않는다.** `'team'` 은
  와이어(어서션·verify-key 응답)에서만 존재하는 값이다(§4.3).

### 2.2 개인 자격의 전달 경로 3원

허브가 신원과 등급을 얻는 길은 셋이고, 각각 신선도가 다르다:

| 경로 | 소유자 | 등급 신선도 | 한도 소비 |
|---|---|---|---|
| 정적 토큰(로컬·자체 운영) | 없음 | 없음 | **미소비**(구조적 무제한) |
| 회원 API 키 `vinc_sk_*` | `user:{public_id}` | verify-key 60초 캐시 | 소비 |
| OAuth 커넥터(claude.ai) | `user:{public_id}` | **승인 시점 동결** | 소비 |

**OAuth 경로의 등급 동결이 결제의 급소다.** 승인 시점의 등급이 인가 코드 →
액세스 토큰 → 갱신 토큰으로 복사되므로, 결제로 Free → Pro 가 되어도 **이미 연결된
claude.ai 커넥터는 옛 등급 그대로다**(갱신조차 옛 값을 재동결한다). 해소는 §9 P0:
허브가 `owner_plan` 저장값을 TTL 로 재조회한다. 이 표는 이미 기록되고 있으나 **아무도
읽지 않는 상태**여서, 판독 훅만 붙이면 된다.

### 2.3 한도 소비 지점

호출 한도는 **MCP `tools/call` 한 곳에서만** 차감된다(핸드셰이크·도구 목록은 무료).
소유자가 없으면 차감 자체를 건너뛰므로 로컬·정적 토큰은 구조적으로 무제한이다.

**차감되지 않는 경로**(현행 유지):

- **웹 Vinc**(계정 프록시 경유) — 계정 측 분당 300회 제한만 있고 등급 무관.
- **동기화** `/sync/push|pull` — 의도적 면제. 팀이 대량 적재해도 막히면 안 된다.
- **커뮤니티 팩 가져오기** — 자체 시간당 10회 제한.

이 비대칭은 **팀 v1 에 유리하게 작용한다**: 팀은 웹 우선이므로 팀 출시에 한도 관련
코드 변경이 0이다(§4.5).

## 3. 주제(domain) 한도

### 3.1 주제란 무엇인가

주제는 **레지스트리가 있는 실체가 아니라 노드의 자유 문자열 열**이다. Episode·Concept·
Record·LearnerPattern 이 각각 `domain` 열을 갖고, **새 문자열로 노드가 써지는 순간
주제가 암묵적으로 생긴다.** "주제 만들기" 호출은 존재하지 않는다.

전역 `Domain` 노드 표가 따로 있으나 이는 소유자 개념이 없는 공용 어휘 노드이며,
**정책이 건드리지 않는다**(기존 불변식).

소유자별 주제 목록은 3개 표(Episode·Concept·Record)의 합집합을 집계해 얻는다
(`api/query.py` 의 domains 계열 플랜). 매 쓰기마다 이 집계를 도는 것은 비싸므로,
개수만 필요한 경로에는 `count(DISTINCT domain)` 전용 플랜을 신설한다.

### 3.2 집행 규칙 (노션식)

1. **한도 도달 시 차단되는 것은 "새 주제 생성"뿐이다.** 기존 주제의 노드 추가·편집·
   문서 적재·검색·동기화는 전부 정상 동작한다.
2. **초과 사용자는 자동으로 유예된다.** 이미 8개를 가진 무료 사용자는 8개를 그대로
   쓰고, 9번째만 막힌다. 데이터 삭제·강제 이관은 없다.
3. **거부는 프래그먼트 단위로 원자적이다.** 한 번의 적재에 새 주제가 둘 포함되어
   한도를 넘으면 그 적재 전체를 거부하고 `domain_limit_reached` 를 돌려준다. 일부만
   반영하는 애매한 상태를 만들지 않는다.
4. **주제 없는 노드는 언제나 허용**한다(주제는 선택 항목이다).

### 3.3 집행 지점

단일 관문은 `Vinc/api/fragment.py` 의 `merge_fragment` 다. 모든 쓰기 경로(MCP 적재·
웹 적재·팩 가져오기·동기화 적용)가 이 함수로 수렴한다.

```
merge_fragment(fragment, *, store, themes, stamp_edges, max_domains=None)
                                                        └── 신규 인자
```

**기본값 `None`(무제한)이 핵심이다.** 이렇게 두면 동기화 적용 경로가 **코드를 한 줄도
고치지 않고 자동 면제**된다. "면제를 잊는 위험"이 "적용을 잊는 안전한 실패"로 뒤집힌다.

| 경로 | 한도 적용 | 근거 |
|---|---|---|
| MCP 적재 · 웹 적재 | **적용** | 신규 주제의 주 생성 경로 |
| 팩 가져오기 | **적용** | 역시 주요 생성 경로. 우회 구멍이 된다 |
| **동기화 적용** | **면제** | 유예된 사용자의 복제를 깨뜨리면 안 된다 |
| 주제 이름 바꾸기 | 불필요 | 전량 개명이라 **개수가 늘 수 없다**(불변 또는 감소) |

> 주제 이름 바꾸기는 소유자의 해당 주제 노드를 **전부** 새 이름으로 옮기는 연산이라
> 옛 이름이 소멸한다. 기존 주제로 합치면 오히려 개수가 준다. 따라서 감시면은
> 적재와 팩 가져오기 **둘뿐**이다. (일관성용 가드를 넣는 것은 무해하나 필수는 아니다.)

### 3.4 한도 값의 해석 위치

**등급 → 숫자 변환은 허브가 한다.** 사이드카는 숫자만 받는 정책 무지 메커니즘으로
남긴다. 한도 설정의 단일 출처를 허브 환경변수로 두기 위함이다.

- 허브 환경변수 `VINC_FREE_MAX_DOMAINS=5` (미설정 = 한도 없음 = 기능 꺼짐)
- 허브가 적재 계열 요청 본문에 해석 결과를 실어 사이드카로 보낸다.

**웹 경로에는 등급 정보가 지금 없다.** 계정이 서명하는 프록시 어서션에는 소유자와
작업 이름만 들어 있다. 여기에 등급 클레임을 **덧붙인다**(구 허브는 무시 → 한도만
미적용되는 안전한 실패, 다른 동작은 불변).

### 3.5 우회 불가성

MCP 커넥터는 계정 프록시를 **거치지 않고** 허브에 직접 붙는다. 따라서 계정 측
미들웨어에만 한도를 걸면 커넥터로 그냥 뚫린다. **허브·사이드카 집행이 유일하게
우회 불가능한 배치**이며, 이것이 §3.3 이 사이드카 함수를 관문으로 고른 이유다.

## 4. 팀 아키텍처

### 4.1 공유 소유자 모델

**팀 그래프의 소유자 문자열은 `team:{uuid}` 다.** 소유자는 불투명 문자열이고 격리는
등치 비교로만 이뤄지므로 **그래프 스키마 변경이 0**이다. 노드 ID 가 내용 기반
(`concept:margiela` 형태로, 소유자 이름공간이 아님)인 것도 팀에는 오히려 이점이다 —
두 멤버가 같은 개념을 각자 적재하면 하나로 병합된다.

기존 격리 2층(읽기 스코프·쓰기 스탬핑)은 그대로 유효하다. 팀 그래프에 접근하는 요청은
소유자가 `team:{uuid}` 로 강제되고, 개인 그래프(`user:{public_id}`)와는 서로 보이지 않는다.

### 4.2 계정이 그래프 소유자를 정한다

지금은 허브가 어서션의 주체(sub)로부터 `user:{sub}` 를 **합성**한다. 팀에서는 이
합성이 성립하지 않으므로, **계정이 멤버십과 역할을 검증한 뒤 그래프 소유자를 직접
서명해 내려보내고 허브는 그것을 신뢰**한다.

### 4.3 어서션은 새 유형으로 분리한다 (급소)

**팀 스코프는 기존 어서션에 필드를 덧붙이는 방식으로 하면 안 된다.**

허브의 웹 프록시 처리는 유형이 `proxy` 가 아니면 거부하고, `proxy` 이면 **무조건**
소유자를 `user:{sub}` 로 강제한다. 여기에 필드만 추가하면 **구 허브 + 신 계정** 조합에서
팀 작업이 조용히 **멤버의 개인 그래프로 흘러간다** — 팀 문서가 개인 그래프에 쌓이고
팀 화면은 빈 결과를 보여준다. 오류가 아니라 **무음 오동작**이라 최악이다.

따라서 팀은 **새 유형**을 쓴다:

| 유형 | 용도 | 구 허브의 반응 |
|---|---|---|
| `proxy` | 개인 그래프(기존, 바이트 동일 유지) | 정상 |
| `proxy-team` | 팀 그래프 읽기·쓰기 | 유형 검사에서 **거부(401)** |
| `purge-team` | 팀 삭제 시 그래프 소거 | 유형 검사에서 **거부(401)** |

이렇게 하면 하위호환 장치 자체가 불필요해지고, 배포 순서를 틀렸을 때의 결과가
**"정확성 문제"에서 "팀 기능이 아직 안 열림"으로 강등**된다.

`proxy-team` 페이로드에 담는 것: 주체(멤버), **그래프 소유자**(`team:{uuid}`),
**역할**, 작업 이름, 등급, 발급·만료 시각. 허브는 그래프 소유자의 형식을 정규식으로
검증하고(`^team:` + UUID), 역할을 §4.4 표로 판정한다.

### 4.4 권한 — 작업(op) 단위 3역할

세밀한 주제별·노드별 권한은 전 질의 플랜 개작이 필요해 v1 범위 밖이다(§1.4). 대신
**이미 이름이 붙어 있는 작업 목록**을 등급별로 가른다.

| 역할 | 허용 |
|---|---|
| **열람자**(viewer) | 모든 조회 작업 + 작업 상태 조회 |
| **편집자**(editor) | 열람자 + 쓰기(고정·태그·터치·활성화·적재·팩적재·문서 저장/추출/재임베딩·근거 백필·관례 생성) |
| **관리자**(admin) | 편집자 + 파괴적 작업(노드 삭제·엣지 삭제·노드 병합·문서 삭제·주제 이름 바꾸기) |

- 집행은 **허브에서 하고**(우회 불가 지점), 계정 프록시에서도 **선차단**한다(이중 방어).
- 팀 그래프 소거는 그래프 작업이 아니다 — 팀 삭제 절차 전용이다(§4.6).
- **드리프트 방지 테스트를 양쪽에 둔다**: 역할 표의 작업 이름 합집합이 프록시 허용
  목록 전체와 일치해야 한다. 새 작업을 추가하면서 역할을 안 정하면 CI 가 깨진다.
  (과거 합계 뷰가 웹에서만 죽었던 사고가 목록 3중 드리프트였다 —
  [[vinc-web-parity-proxy-allowlist]] 계열 교훈.)

### 4.5 한도와 팀

팀 v1 은 웹 우선이고 웹 경로는 한도를 차감하지 않으므로(§2.3), **팀 출시에 한도
관련 변경이 없다.** 다만 키 설계만 미리 확정해 둔다:

- 개인: `user:{public_id}` — **기존 그대로. 기존 카운터 행 이관이 영구히 불필요하다.**
- 팀-MCP(후속): `team:{uuid}#user:{public_id}` 복합 키. 한 멤버가 팀 전체 몫을
  소진하는 것도, 팀 작업이 개인 몫을 갉아먹는 것도 막는다.

### 4.6 삭제·소거의 폭발 반경

- **멤버가 자기 계정을 지워도 팀 그래프는 안전하다.** 현행 소거 경로는 주체에서
  `user:` 소유자만 유도할 수 있어 팀 소유자를 만들 방법이 구조적으로 없다.
  이 성질을 **테스트로 고정**한다(멤버 삭제 후 팀 그래프 잔존 확인).
- **팀 소유자의 계정 삭제는 차단**한다(409). 팀을 먼저 삭제하거나 소유권을 넘겨야 한다.
- **팀 삭제 순서**(계정 삭제와 동형, 실패 시 중단): 결제사 구독 해지 → 팀 그래프 소거
  확인 → 팀·멤버십·초대 레코드 삭제.
- **저작자 기록이 없다.** 팀 그래프의 노드는 소유자가 팀이라 "누가 썼는가"가 남지
  않는다. v1 은 이를 수용하고 **계정 감사 로그에 행위자를 남기는 것으로 보완**한다.
  결과적으로 **멤버를 제명해도 그 사람의 기여는 팀 그래프에 남는다** — 이는 제품
  정책이자 개인정보 고지 사항이다(§11.1). v2 에서 선택적 저작자 각인을 검토한다.

### 4.7 데스크탑이 v1 에서 빠지는 이유

로컬 저장소는 **한 저장소 = 한 소유자**를 전제로 만들어져 있다:

- 동기화 커서(push·pull)와 동기화 대상 주제 선택이 **저장소 전역 단일 키**다.
  개인 그래프와 팀 그래프를 한 기기에서 동시에 동기화하면 커서가 충돌한다.
- 동기화 기준 스냅샷의 기본키가 노드 ID 단독이라, 같은 노드 ID 의 개인본·팀본이
  한 저장소에 공존할 수 없다.

해소는 **커서·주제선택 키를 소유자별로 잇는 것**(`cursor:push:{owner}` 형태)과
기준 스냅샷 키에 소유자를 더하는 것이다. 국소적이지만 마이그레이션을 동반하므로
팀 GA 이후로 미룬다.

한편 **다중 작성자 화해 기계는 이미 있다.** 필드 단위 3-way 병합·HLC·툼스톤이
웹과 데스크탑의 동시 편집을 이미 처리하고 있어, **팀의 여러 멤버가 웹에서 동시에
쓰는 것에는 새로운 충돌 처리가 전혀 필요 없다.**

dbmate 전진 전용. 다음 번호는 **011**. 아래는 착지 순서 기준 번호이며, 실제 착지

| # | 마이그레이션 | 내용 |
|---|---|---|
| 011 | `subscriptions` | `ARCHITECTURE.md#§4.5` DDL + `seats INT NULL` · `cancel_at_period_end` · `last_event_at DATETIME(3)`(역순 웹훅 가드). `user_id` = **대금 지불자**(팀 구독도 지불자는 소유자 개인) |
| 012 | `webhook_events` | `(provider, event_id)` UNIQUE, `type`·`payload`·`status('received','processed','failed')`·`occurred_at`·`processed_at`. **멱등의 근거** |
| 013 | `teams` | `public_id BINARY(16)` UNIQUE · `owner_user_id` FK · `name` · **`graph_owner VARCHAR(64)` UNIQUE**(생성 시 `team:{uuid}` 확정 저장) · `status('pending','active','suspended','deleted')` |
| 014 | `team_members` | `(team_id, user_id)` UNIQUE · `role ENUM('viewer','editor','admin')` · `status`. **소유자도 admin 행으로 포함**(시트 1 점유 — 균일 계산) |
| 015 | `team_invites` | `team_id` · `email` · `role` · 토큰 연결 · **`status('sent','failed','accepted','revoked','expired')`** · `invited_by` |
| 016 | `auth_tokens.purpose` 확장 | `+'team_invite'`. 초대는 **아직 계정이 없을 수 있는 이메일로 키잉**되므로 이 표의 설계 의도와 정확히 맞고, 원자적 소비 헬퍼를 그대로 재사용한다 |
| 017 | `subscriptions.team_id` | `BIGINT NULL` + FK. NULL = 개인 구독 |

**015 의 `status` 가 단순 편의가 아니다.** 메일 발송기는 수신거부 목록에 걸린 주소로의
발송을 조용히 버리고 **절대 예외를 던지지 않는다**(열거 방지 설계). 초대는 기존 템플릿과
달리 **제3자 주소로 나가므로**, 이 침묵이 그대로 "초대했는데 아무 일도 안 일어남"이
된다. 발송 결과를 이 열에 적고 팀 화면에 표시·재발송을 제공한다.

## 6. 결제 설계

### 6.1 결제사 추상화

내부 구독 실체를 먼저 정의하고 결제사를 **꽂아 쓰는** 구조로 간다.

```
provider 인터페이스
  createCheckout(plan, seats, user) → 결제 페이지 URL
  cancel(subscription)
  updateSeats(subscription, n)
  verifyWebhook(rawBody, headers) → boolean
  parseEvent(rawBody) → NormalizedEvent   // 결제사 이벤트 → 내부 전이
```

구현체는 `paddle` 로 시작하고 `toss` 를 나중에 더한다. 상위 로직(상태기계·투영·시트)은
결제사를 모른다.

### 6.2 구독 상태기계

```
incomplete ──첫 결제 성공──▶ active ◀──복구 결제── past_due
    │                        │  │                    │
    └─방치─▶ incomplete_expired│  └─결제 실패─▶ past_due└─유예 7일 만료─▶ canceled
                              └─해지 예약(기간말)──────────────▶ canceled
```

- 상태 열거값은 `ARCHITECTURE.md#§4.5` 를 그대로 쓴다.
- **유예 7일**: `past_due` 동안 자격을 유지한다(투영 미변경). 만료 시 개인은
  `users.plan='free'`, 팀은 `teams.status='suspended'`.
- **팀 정지의 의미**: 데이터는 보존하고, **계정이 팀 어서션 서명을 멈춘다.**
  허브는 관여하지 않는다(정지 판정이 계정 한 곳에만 있다).
- Paddle 의 일시정지(pause)는 내부 열거값에 없으므로 **결제사 대시보드에서 기능 자체를 끈다**.

### 6.3 웹훅 수신

- **경로 예외 등록이 필수다.** 계정의 1차 출처 가드가 Origin 없는 요청과 JSON 아닌
  본문을 거부하는데, 결제사 콜백은 둘 다 해당한다(특히 폼 인코딩을 쓰는 국내 결제사).
- **서명 검증은 원문 본문으로** 한다(기존 Resend 웹훅 처리가 같은 형태다 — 그대로 본뜬다).
- **멱등은 DB 로** 한다. 계정의 속도 제한·중복 판정은 프로세스 메모리라 재기동에
  살아남지 못한다. `webhook_events` 의 UNIQUE 제약이 유일한 근거다.
- **역순 도착 가드**: 이벤트의 발생 시각이 저장된 `last_event_at` 보다 이르면 버린다.
- 처리 실패는 `failed` 로 남겨 수동 재생이 가능하게 한다.

### 6.4 시트 관리

- 초대 생성은 **팀 행을 잠근 트랜잭션 안에서** 현원 + 발송 대기 초대 < 시트 수를
  확인한다(동시 초대 경합 차단).
- 시트 축소는 현원 미만으로 못 내린다(409).
- 시트 증가: Paddle 은 수량 갱신으로 일할 계산을 위임한다.

### 6.5 계정 삭제 순서 (의무)

`ARCHITECTURE.md#§4.5` 의 하드 룰이다: **결제사 구독 해지가 DB 삭제보다 먼저**.
현재 삭제 절차는 그래프 소거 → 메일 신원 정리 → 하드 삭제이므로, 그래프 소거와
메일 정리 사이에 **구독 해지를 끼우고 실패 시 중단**한다(그래프 소거와 동일한
실패 시 중단 방식 — 해지가 확인 안 되면 503 을 돌리고 계정을 지우지 않는다).
안 그러면 사라진 계정에 청구가 계속된다.

### 6.6 Toss 추가 시 설계 (2단계)

Toss 는 구독 객체를 주지 않는다. **정기 청구를 우리가 돌린다.**

- **빌링키는 카드 전용**이다. 계좌이체·가상계좌로는 정기 결제를 못 만든다(연 1회
  청구서 결제로만 쓴다).
- 구독 식별자는 우리가 발급한다(`toss:{uuid}`), 고객 키는 결제사 규약을 따른다.
- **청구 시도 표**(`charge_attempts`)를 둔다: `(구독, 청구주기, 시도번호)` UNIQUE +
  주문번호 UNIQUE. **결제사가 주문번호 중복을 거부하므로 이중청구 방어가 공짜로 성립**한다.
- **크론은 시간당 1회**, MySQL 전역 잠금(`GET_LOCK`)으로 단일 실행을 보장한다.
  계정 컨테이너가 1 인스턴스 전제지만, 잠금을 쓰면 늘려도 안전하고 커넥션이 죽으면
  자동 해제된다.
- 재시도 사다리 D+1 · D+3 · D+5, 소진 시 `past_due`.
- 같은 크론 루프에서 **결제사 무관 투영 스윕**을 돈다(유예 만료·해지 예약 만료 →
  투영 갱신). Paddle 웹훅 유실 시의 안전망을 겸한다.
- **1 MID = 1 통화** 제약이 있다. 원화와 달러를 같이 받으려면 MID 와 결제창 인스턴스를
  통화별로 따로 둬야 한다. 주문 모델을 처음부터 그 전제로 짠다.
- 운영 선행조건(사업자등록 → PG 계약 → 통신판매업 신고, 해외카드 별도 심사 10~14
  영업일)은 개발과 **병행 착수**한다.

이니시스는 후순위 대안으로만 남긴다: 공개 개발 문서가 빈약하고 리셀러 경유 관행이라
1인 개발 기준 마찰이 크다. 강점은 아시아권 지갑(알리페이·위챗·라인) 지원이므로,
그 시장이 필요해지면 재평가한다.

### 6.7 명명 제약

- 계측 식별자 `usage_record` · `token_margin` · `UsageRecord` 는 **반입 금지**다
  (F1 하드 룰, [[vinc.a.terms]] §4). 청구 관련 표·클래스를 이 이름으로 만들지 않는다.
  현재 설계의 이름(`subscriptions` · `webhook_events` · `charge_attempts`)은 안전하다.
- 사이드카에 자격 관련 표면을 만든다면 **`/entitlements`** 로 명명한다.
  `/plan/{kind}` 는 이미 **질의 플랜 조회** 라우트다(충돌 주의).

## 7. 국가·통화 매칭

### 7.1 왜 Paddle 단독으로 시작하는가

| 후보 | 판정 | 근거 |
|---|---|---|
| Stripe | **불가** | 한국 소재 판매자를 받지 않는다. 해외 법인 설립이 전제 |
| PayPal | **국내 불가** | 한국 판매자는 **한국 구매자로부터 수취할 수 없다**. 글로벌 전용이고 실효 수수료도 높다 |
| Toss | 국내 최적 | 1단계에서는 사업자 서류·심사 리드타임이 출시를 막는다 |
| **Paddle(MoR)** | **채택** | 한국 개인 판매자 가입 가능, 한국 구매자에게 한국 카드·간편결제 제공, 원화 청구 가능, **한국 부가세 포함 100여 개국 세금을 대신 신고·납부** |

Paddle 은 **등록 판매자(MoR)** 라 법적 판매자가 Paddle 이다. 세금 처리가 통째로 넘어가는
것이 1인 운영에서 가장 큰 이점이다. 대가는 수수료(5% + 건당 $0.50, 실효 약 7%)와
**정산 통화가 달러**라는 점이다.

**건당 고정 수수료가 저가 월간제에 불리하다.** 그래서 §1.3 가격표는 연간 결제를
확실히 유리하게 잡았고(월 대비 약 17% 할인), 결제 화면도 연간을 기본 선택으로 둔다.

### 7.2 라우팅 원칙

1. **결제 국가는 사용자가 신고한 값이 정본이다.** 세금 판정의 방어 가능한 근거는
   이것뿐이다.
2. **IP·언어 설정은 기본값 미리 선택에만 쓴다.** 최종 판정에 쓰지 않는다.
3. **통화는 국가를 따른다**(그 반대가 아니다).

### 7.3 단계별 배치

**1단계(Paddle 단독)** — 전 국가가 Paddle 결제창을 탄다. 한국 접속자에게는 원화로
표시하고(원화 청구 지원), 그 외에는 달러로 표시한다. 결제 국가 신고와 세금 처리는
Paddle 결제창 안에서 끝난다.

**2단계(Toss 추가)** — 결제 페이지에서 결제 국가를 고르고, 한국이면 Toss(원화),
그 외는 Paddle 로 보낸다. **기존 Paddle 한국 구독자는 그대로 둔다** — 강제 이전은
카드 재등록을 요구해 이탈을 부른다(업계 관측 5~15%). 신규 가입만 새 경로로 흘린다.

## 9. 롤아웃 P0~P4

각 단계는 **독립 배포 가능**하고, 켜는 스위치가 따로 있다.

### P0 — 등급 배관 정비 (사용자 가시 변화 0)

목적: 값 공간을 미리 넓히고 **OAuth 등급 동결을 푼다**. 배포 순서 **허브 → 계정**.

  **재연결 없이 기존 커넥터가 5분 내 새 한도를 따르는지** 실측.

### P1 — Free 한도 상향 + 주제 상한 (스위치: 환경변수 존재 여부)

- 사이트 문구 정정(7곳, §8.3).
- **검증**: 신규 테스트(상한 도달 시 새 주제 거부 / 기존 주제 편집 허용 / 한 프래그먼트
  내 신규 2개 원자 거부 / 동기화 무영향 / 이름 바꾸기 개수 불변 / 팩 가져오기 거부) ·
  기존 격리 테스트 통과 · 라이브 실측(16번째 호출 성공, 6번째 주제 거부).

### P2 — 결제 기반 + 개인 Pro (스위치: `BILLING_ENABLED`)

- 마이그레이션 011·012.
- 결제사 추상화 + Paddle 구현 + 웹훅 + 상태기계 + 투영 + 계정 삭제 순서 삽입.
- 환경변수·시크릿 **코드 배포 전에** 수동 설정.
- **검증**: 샌드박스 결제 왕복(결제 → 웹훅 → 투영 → `/api/me` → **P0 덕분에 기존
  MCP 토큰이 5분 내 반영**) · 같은 이벤트 재전송 시 두 번째가 무동작 · 서명 불량 거부 ·
  해지 → 기간말 → 투영 · **계정 삭제가 구독 해지를 선행하는지** 샌드박스 단언.

### P3 — 팀 (스위치: `TEAMS_ENABLED`, 마지막에 켠다)

- 마이그레이션 013~017.
- 허브 먼저 배포(새 어서션 유형·역할 표·팀 소거) → 계정 배포 → **스위치는 최후**.
  §4.3 유형 분리 덕에 순서를 틀려도 "아직 안 열림"일 뿐 오동작하지 않는다.
- 초대·수락·역할·시트·팀 삭제·소유자 계정 삭제 차단.
- 수락 흐름: 로그인(기존 매직 링크가 계정 생성을 겸한다) → 토큰 원자 소비 →
  **세션 이메일과 초대 이메일 일치 확인** → 시트 재확인 → 멤버 등록.
  로그인 후 흐름 재개는 기존 관례(브라우저 저장소에 대기 상태를 두고 재생)를 따른다 —
  열린 리다이렉트를 만들지 않기 위해 `?next=` 를 쓰지 않는 것이 기존 불변식이다.
- **검증**: 소유자 유도 계약 테스트 갱신 + 팀 케이스 · 구식 유형 거부 · 열람자의
  쓰기 거부 · 시트 소진 시 초대 거부 · **멤버 계정 삭제 후 팀 그래프 잔존** ·
  수신거부 주소 초대 시 상태가 `failed` 로 표시.

### P4 — 표면·문서·국내 결제

- 가격 페이지·계정/팀 화면·데스크탑 등급 배지·개인정보 문구.
- Toss 추가(§6.6) — 사업자 서류는 P2 와 병행 착수.

## 11. 법무·운영 미결

### 11.1 팀 공유 그래프의 고지 (P4 전 처리 필수)

- 멤버가 넣은 내용은 **팀 전체에 보인다.**
- **제명·탈퇴 후에도 그 사람의 기여는 팀 그래프에 남는다**(§4.6 저작자 미기록의 귀결).
- 팀 삭제 시 팀 그래프는 소거된다.

이 셋을 개인정보 처리방침·이용약관·팀 초대 화면에 명시한다. 초대 수락 화면에서
사용자가 이 사실을 알고 수락하게 하는 것이 요점이다.

### 11.2 금지 어휘 정본 개정 (F1)

[[vinc.a.terms]] §4 는 `과금`·`결제`·`구독`·`요금제` 를 하드 룰로 금지하고 근거를
**"Vinc 자체 과금 표면 부재"** 로 적고 있다. 본 결정으로 그 전제가 소멸한다.

실행 게이트(`Vinc/scripts/gate_forbidden.py`)는 **이미 이 넷을 검사 토큰에서 제외**했고
(정책 문서가 그 어휘로 금지를 서술해 오탐이 컸다는 실무 이유), 실제 금지는 계측
식별자 3종뿐이다. 즉 **코드 게이트는 결제 도입을 막지 않는다.** 다만 문서와 게이트를
동기화한다는 규약이 있으므로, `vinc.a.terms` §4 의 F1-d~g 항목을 **"결제 표면 신설에
따라 해제(계측 식별자 F1-a~c 는 영구 금지 유지)"** 로 개정한다. 이 개정은 P2 착수 전에.

### 11.3 확인이 필요한 외부 사실

| 항목 | 상태 |
|---|---|
| Paddle 원화 정산 가능 여부 | 공식 문서는 정산 통화를 달러·유로·파운드·호주달러·캐나다달러로 한정. 원화 정산 가능하다는 국내 블로그 서술과 상충 — **Paddle 에 직접 확인** |
| MoR 경유 판매 시 통신판매업 신고 요부 | 세무사 확인 필요. 국내 직접 판매(2단계 Toss)에는 신고가 필요하다는 것이 명확 |
| 해외 매출의 국내 세무 처리 | 용역 수출(영세율) 해석이 통설이나 **세무사 확인 후 확정** |
| PayPal 한국 계정의 정기결제 지원 | 미확인. 채택하지 않으므로 당장은 무관 |
| Stripe 의 MoR 상품이 한국 판매자에게 열리는지 | 열리면 2결제사 구조를 하나로 접을 수 있다 — **주기적 확인 가치 있음** |

### 11.4 운영 전제

- **허브는 단일 레플리카 전제다.** 상태 저장소가 파일 기반이고 속도 제한이 프로세스
  메모리라 복제하면 깨진다. 배포 문서에 명문화한다([[vinc-deployment-policy]] 계열).
- 지원 메일 주소가 **수신 불가**다(MX 없음). 결제 도입 시 환불·청구 문의가 들어오므로
  **P2 전에 수신 경로를 만든다.**
