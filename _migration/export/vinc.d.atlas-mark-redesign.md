# Atlas 마크 언어 재검토

> **지위: 연구 입력(research-input).** 채택은 발주자 결정(DEC)으로만 정본화된다.
>
> 발주자 질문(2026-08-03): "3D 노드의 유리 같은 구, 선의 얇은 실 같은 표현이 이
> **데이터 뷰**에서 좋은 것이 맞는가. 왜 이것을 그대로 유지하는가. 옵시디언으로
> 온톨로지를 구축하는 사례를 조사해 맞지 않는 것을 재설계하라."
>
> 정당한 지적이다. 선행 작업(D75·D76, 가시성)은 **닫힌 층(D35 형태=타입 · D40 유리 ·
> D33 헤어라인 · D20 모노크롬)을 전제로 두고 그 안에서 대비만 고쳤다.** 그 전제 자체가
> 검증된 적이 없다. 이 문서가 그 검증이다.

## §0 요약 — 결론 먼저

**세 가지가 데이터 뷰의 목적과 어긋난다.**

1. **유리(D40)는 기본 테마에서 아예 렌더되지 않는다.** 코드 실측: `MeshPhysicalMaterial`
   을 만드는 `material()` 은 `nodeObject` 의 **비-글로우 분기에서만** 불린다
   (`atlas3d.ts:249,253`). 다크 글로우 분기는 그 앞에서 조기 반환하며
   **`MeshBasicMaterial`(무조명 평면)** 을 쓴다(`:224`). 기본 테마는 다크다(D38).
   ⇒ **제품의 기본 화면에 유리는 없다.** 발주자가 "유리 같다"고 본 것은 평면 fill +
   가산 글로우 스프라이트다. 우리는 두 재질 체계를 유지하는 비용을 내면서 간판
   격인 쪽을 비기본 테마에서만 쓰고 있다.
2. **헤어라인(D33)은 폭 채널을 0으로 못 박아 데이터를 실을 자리를 없앴다.**
   `linkWidth` 가 0 이면 THREE.Line 이고, 그 위에 얹으려던 "농도=가중치" 사다리는
   **`weight` 를 채우는 코드가 없어 사문**이다(`atlas.ts` `toL3` 가 weight 를 안 싣는다).
   즉 3D 엣지는 **폭도 농도도 데이터를 안 나른다** — 방향 여부와 크로스 여부 2비트뿐이다.
3. **형태=타입(D35)은 가장 약한 채널에 가장 중요한 정보를 실었다.** 형태는
   "probably preattentive"(크기·명도보다 한 급 아래)이고 축소에서 먼저 무너진다.
   게다가 실 데이터의 타입 분포는 **개념 60% · 레코드 22% · 에피소드 18%**
   (Bridge·Entity 0) — 열에 여섯이 같은 형태라 변별할 것이 애초에 적다. 2D 에는
   형태 채널이 존재하지도 않는다.

**공통 진단: 렌더 예산이 물성(유리·대기·3D 깊이)에 가 있고 데이터 채널(타입·가중치·
상태)에는 안 가 있다.** 옵시디언이 못 가진 것을 Vinc 는 가지고 있는데(타입 노드·타입
엣지) 화면이 그것을 안 쓴다.

## §1 코드가 실제로 그리는 것 (실측)

| 주장 | 실측 | 앵커 |
|---|---|---|
| 다크 기본 화면에 유리가 쓰인다 | **거짓.** `material()`(MeshPhysical) 호출은 249·253 두 곳뿐이고 둘 다 글로우 분기 **뒤**다. 다크는 224 에서 `MeshBasicMaterial` 로 만들어 조기 반환 | `atlas3d.ts:224,249,253` |
| 249 의 유리가 쓰이는 조건 | 라이트 테마, 또는 `mountMinis3d`(호출자 0 — 사문) | `:323`(glow=true) vs `:579`(기본 false) |
| 253 의 유리 링 | `kind === "domain"` 전용인데 `/graph` 는 domain 을 내보내지 않는다 — **사문** | `query.py:514` |
| 엣지 폭이 데이터를 나른다 | **거짓.** `linkWidth` 는 사용자 배율(edgeScale)만 반영하고 기본 0(헤어라인) | `atlas3d.ts` linkWidth |
| 엣지 농도가 가중치를 나른다(D33) | **거짓 — 사문.** `l.weight` 분기가 있으나 `toL3` 가 weight 를 안 싣는다 | `atlas.ts` `toL3` |
| 타입 5종이 형태로 갈린다 | **부분.** 실 데이터는 3종만 존재(개념 148 · 레코드 53 · 에피소드 44), Bridge·Entity 0. 2D 는 전부 원 | `vinc_domains` 실측 · `atlas2d.ts` |

즉 **닫힌 층이라 지켜 온 규약의 상당 부분이 이미 화면에 없다.** 지키고 있던 것은
규약이 아니라 규약의 기억이다.

## §2 외부 조사 — 옵시디언 온톨로지 실무가 알려주는 것

### 2.1 옵시디언 그래프의 실패는 "예쁘지만 쓸모없다"로 요약된다

널리 인용되는 비판(Code Culture, "Obsidian's Graph View Is Beautiful and Almost
Completely Useless")의 진단은 셋이다.

- **운영 메타데이터 부재** — "노드 상태를 안 보여준다. 우선순위를 안 보여준다."
  초안인지 완성인지 구분이 없다.
- **규모 붕괴(hairball)** — 50개 미만에서는 잘 작동하고, **200개를 넘으면** 힘-지향
  배치가 "보기엔 재밌지만 항해할 수 없는 엉킨 실뭉치"가 된다. 노드가 서로 구별되지
  않고 개별 연결이 밀도에 묻힌다.
- **탐색 비효율** — "이름으로 검색하지 않고서는 연결이 많은 MOC 와 보통 노트를
  **구별할 수 없다**." 시각 탐색의 존재 이유가 무너진다.

작동하는 것으로 꼽힌 둘: **타입 링크로 위계를 만드는 것**(ExcaliBrain — 부모/자식/
형제), 그리고 **국소 그래프**(현재 노트 주변만 — "어떤 규모에서도 쓸모가 유지된다").

### 2.2 옵시디언의 구조적 한계 = Vinc 의 강점

PKG(개인 지식그래프) 실무자들이 반복해 지적하는 옵시디언의 한계는 정확히 이것이다.

> **엔티티 타입이 없다** — 모든 노드가 그냥 '노트'다. 사람이든 프로젝트든 개념이든
> 초안이든 같다. 그리고 **타입 링크가 없다** — 관계 자체에 메타데이터를 붙일 수 없다.

Vinc 는 **둘 다 가지고 있다**(노드 5종 · 엣지 6종 + role·confidence·evidence).
그런데 화면은 그 우위를 **가장 약한 채널(형태)에, 가장 약한 조건(모노크롬·축소)** 에
실어 사실상 버리고 있다. 옵시디언이 못 해서 못 보여주는 것을, 우리는 할 수 있는데
안 보여준다.

### 2.3 온톨로지 시각화 도구의 표준 관례는 "색 = 타입"

WebVOWL(RDF 온톨로지 시각화)은 **노드 색과 선 스타일을 달리해 엔티티·속성·관계를
변별**한다. Neo4j Bloom, yFiles 계열 가이드도 공통으로 "색은 범주·클러스터·위계에
쓰고, 시각 부호화(색·크기·형태)로 의미를 즉시 전달하라"고 권한다. 즉 **타입 그래프에서
색=타입은 예외가 아니라 기본형**이다.

Vinc 의 모노크롬(D20·D39)은 그 반대 선택이다. 근거는 있었다 — 공유 팩이 어디서나
같게 읽혀야 하고(브랜드·결정론), 색상환 남용을 막는다. 그러나 **닫힌 5종 타입 어휘에
고정 색을 주는 것**은 임의 데이터 채색과 다르다. 결정론적이고 공유 가능하며,
색맹 대응은 **중복 부호화**(색 + 형태 + 라벨)라는 표준 처방이 이미 있다.

### 2.4 물성·3D 효과에 대한 증거는 "무해하지만 무익"에 가깝다

Tufte 의 data-ink 원칙(비데이터 잉크 최소화)은 영향력에 비해 **근거가 자기 관찰
하나**라는 비판을 받아 왔고, 후속 실험(1994·2013·2015)은 chartjunk 가 **항상 해롭지는
않으며 기억성·몰입을 높일 수도 있다**고 뒤집었다. 다만 같은 실험들이 3D 효과의
**정확도 이득은 확인하지 못했다**.

⇒ 유리·글로우를 "죄악"이라 부를 근거는 없다. 그러나 **정확도를 높이지도 않는다.**
따라서 판단 기준은 미학이 아니라 **기회비용**이다: 그 예산이 데이터 채널을 밀어내고
있는가. Vinc 에서는 밀어내고 있었다 — 유리의 반투명(0.72)이 fill 을 배경 대비
아래로 끌어내린 것이 D76 에서 고친 문제의 일부다.

### 2.5 엣지: 폭은 실재하는 채널이고, 3D 에서는 기술적 제약이 있다

그래프 판독 실험 문헌의 공통 지적은 **엣지 수가 복잡도의 주범**이며 hairball 은
"10~15 노드에서도" 발생한다는 것이다. 완화책으로 실증된 것은 **번들링·압축·강조
(하이라이트)** 다. 즉 선을 얇게 만드는 것은 완화책이 아니다 — 얇게 만들면 교차가
줄지 않고 **판독만 어려워진다**.

기술 제약도 있다: WebGL 에서 `THREE.Line` 의 선 폭은 대부분 플랫폼에서 **1px 로
고정**된다(`linewidth` 무시). 그래서 D33 이 "튜브가 뚱뚱하다"는 문제를 폭 0 으로
해결한 것은 **선택지가 둘뿐이라 생긴 이분법**이었다. 실제 선택지는 셋이다:
뚱뚱한 튜브 / 1px 헤어라인 / **Line2 계열(화면 공간 폭을 가진 얇은 사각 스트립)**.

## §3 채널 예산 분석 — 무엇이 무엇을 밀어냈나

데이터 뷰의 채널은 유한하다. 지금 배분은 이렇다.

| 채널 | 현재 싣는 것 | 평가 |
|---|---|---|
| 위치 | 도메인 위계(D74 폭발 배치) | **좋다** — 가장 강한 채널에 가장 구조적인 정보 |
| 크기 | 연결수 √ | **좋다** — 정량에 맞는 채널 |
| 색상(hue) | **아무것도** (모노크롬) + 초점 1점 | **낭비** — 타입 그래프에서 가장 표준적인 타입 채널이 비어 있다 |
| 명도 | 깊이 티어(near/mid/far) | 타당하나 티어는 파생 정보(=연결수 재탕) |
| 형태 | 타입 5종 | **과적재** — 약한 채널 + 실 데이터는 3종 + 2D 엔 부재 + 축소 시 소멸 |
| 재질 | **아무것도**(유리는 물성일 뿐) | **낭비** — 게다가 기본 테마엔 렌더도 안 됨 |
| 선 폭 | **아무것도**(0 고정) | **낭비** |
| 선 농도 | 방향/크로스 2비트 (가중치 분기는 사문) | 저활용 |

**색상·재질·선 폭 세 채널이 비어 있고, 형태 하나가 과부하다.** 이것이 "구별이 안
된다"의 구조적 원인이다 — 대비(D76)를 고쳐도 남는다.

## §4 재설계 제안

원칙 셋을 먼저 세운다.
① **물성은 데이터를 싣지 않으면 뺀다**(정확도 이득 없음 + 기회비용 있음).
② **타입은 강한 채널로 옮기고, 형태는 중복 부호화로 남긴다**(색맹·인쇄 대응).
③ **선은 얇게 만드는 대신 수를 줄인다**(문헌: 완화책은 번들링·필터·강조이지 감량이 아니다 —
   범례 필터(D74)가 이미 그 자리에 있다).

| # | 제안 | 내용 | 성격 |
|---|---|---|---|
| **M1** | **유리 은퇴(그래프 한정)** | 노드 재질을 평면+외곽선으로 통일한다. 다크는 이미 그렇고, 라이트만 맞추면 **두 재질 체계가 하나로 준다**. D37 Liquid Glass 는 **크롬 층에 그대로 유지** — 거기서는 물성이 곧 목적이다 | 정리 · 저비용 |
| **M2** | **타입 = 색(닫힌 5색) + 형태(중복)** | 개념·에피소드·레코드·다리·엔티티에 **고정 hue 5개**를 준다. 결정론이라 공유 팩도 같게 읽히고, 형태는 그대로 두어 색 없이도 읽힌다. 모노크롬 규율은 **"임의 채색 금지"로 재정의**하고 초점색 1점 규칙은 유지(초점은 명도·글로우로 승격) | **닫힌 층 개정 — DEC 필요** |
| **M2′** | (보수 대안) **타입 = 채움 대 외곽선** | 색을 안 열 경우: 개념=채움 · 기록물=외곽선만 · 다리=이중 외곽선. 2상태 채널이라 축소에도 살아남고 모노크롬 유지 | 대안 |
| **M3** | **선 폭을 되살린다** | 3D 는 Line2 계열(화면 공간 폭)로 바꿔 방향/무방향/크로스를 **폭으로도** 가른다. 2D 는 이미 폭 사다리가 있다. 헤어라인 고정(D33)은 "튜브 아니면 1px" 이분법의 산물이었다 | D33 개정 |
| **M4** | **사문 채널 정리** | `weight` 를 실어 농도 사다리를 살리거나, 못 실으면 분기를 지운다. `mountMinis3d`·domain 링도 함께 | 정리 |
| **M5** | **hairball 대비책을 채널이 아니라 상호작용으로** | 문헌 처방(번들링·필터·강조) 중 Vinc 에 이미 있는 것: 범례 필터(D74)·국소 그래프(L2). **국소 그래프를 기본 진입으로 승격**하는 안을 검토한다 — 옵시디언 실무에서 "어떤 규모에서도 쓸모가 유지되는" 유일한 뷰였다 | 별건 검토 |

### 4.1 M2 를 권고하는 이유 (그리고 반론)

권고: **M2(색=타입)**. 근거는 §2.2 — 옵시디언 대비 Vinc 의 유일한 구조적 우위가
타입인데 그것을 안 보여주는 것은 제품 논리에 어긋난다. 그리고 §2.3 — 타입 그래프의
업계 표준이 그렇다.

정직한 반론 셋과 답:
- *"모노크롬은 브랜드다"* → 닫힌 5색은 브랜드 팔레트 **안에서** 고를 수 있다
  (현 토큰에 이미 periwinkle·indigo·ok·warn·danger 계열이 있다). 임의 채색이 아니다.
- *"색맹"* → 중복 부호화(형태 유지 + 라벨)로 표준 처방을 따른다. 게이트에 색쌍
  구분도(ΔE 또는 CVD 시뮬레이션) 검사를 추가할 수 있다.
- *"공유 팩이 다르게 보인다"* → 색이 **타입에 고정**되면 오히려 같게 보인다.
  깨지는 것은 사용자가 색을 고를 때인데, 그건 열지 않는다.

### 4.2 하지 말 것

- 색상환을 여는 것(도메인마다 색) — 도메인은 20개까지 늘 수 있고 그건 채색이
  아니라 무지개다. **도메인은 위치가 이미 표현한다**(D74).
- 3D 를 없애는 것 — 이 문서의 범위 밖이며, 조망·공간 기억이라는 별개 근거가 있다.
- 유리를 크롬에서까지 걷는 것 — D37 은 콘텐츠 평면이 아니라 부유 크롬 전용이고
  거기서는 물성이 목적이다.
