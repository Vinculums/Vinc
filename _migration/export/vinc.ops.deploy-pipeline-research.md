# DEPLOY-PIPELINE-RESEARCH — 배포 파이프라인 고도화 연구

> **지위: 연구 입력(research-input).** as-built 기록인 `DEPLOYMENT.md` 와 달리 이 문서는
> **"지금 수동이거나 취약한 지점"의 진단과 권고**다. 채택은 발주자 결정으로만 정본화된다.
> 조사일 2026-07-29, 전 항목 실측(파일 인용·API 응답) 기반 — 추측 없음.
>
> 배경: 2026-07-28/29 Azure 이관으로 표면 2~4 에 **처음으로 CD 가 생겼다**. 그 과정에서
> "자동화된 것과 여전히 사람 손에 남은 것"의 경계가 드러났고, 그 경계를 전수 조사한 것이
> 이 문서다. **배포 자동화·CI 개선은 지금까지 어떤 DEC·백로그에도 등재된 적이 없다** —
> 이 문서가 최초 등재다.

---

## §0 요약 — 무엇을 발견했나

파이프라인은 이미 **성숙한 축**에 속한다. 인정할 것부터: 업데이터 서명 강제(무서명 릴리스
차단), 3-OS 실런타임 스모크(`/health=="ok"`), 저장 할당량 회피를 위한 릴리스 직접 업로드,
고정 별칭 자산, 오래된 릴리스 자동 아카이브, OIDC 키리스 인증, SWA 토큰 런타임 조회 —
전부 실패를 겪고 나서 그 실패를 막도록 설계된 흔적이다.

그럼에도 **15개 지점**이 수동이거나 취약하다. 성격별로 셋:

| 성격 | 대표 항목 | 성질 |
|---|---|---|
| **조용히 틀리는 것** | 498건 테스트가 CI 에 없음 · `package-lock.json` 7릴리스 방치 · `mk_alias` 실패해도 초록 · 웹/데스크탑이 같은 버전을 주장 | 사고가 나도 **초록으로 통과**한다 — 가장 위험한 부류 |
| **단일 실패점** | `TAURI_SIGNING_PRIVATE_KEY` 백업 절차 0건 · PAT 2종 만료 미관리 | 터지면 **복구 경로가 없거나** 릴리스 당일에야 발견 |
| **전제가 깨진 결정** | DEC D44($0 코드서명 경로) — 전제였던 "리포 public" 이 **실제로는 private** | 결정을 재검토해야 한다 |

**가장 큰 갭 하나만 고른다면**: 파이썬 테스트 **498건이 어떤 CI 에도 물려 있지 않다**.
사람이 기억해서 `python verify.py` 를 칠 때만 돈다.

## §1 데스크탑 릴리스

### 1.1 ⚠ DEC D44 의 전제가 깨졌다 — 코드 서명 재결정 필요

**D44(2026-07-13 채택)** 는 $0 경로를 확정했다: `Vinclums/Vinc` **public 전환** →
Windows = **SignPath Foundation 무료 OSS 서명**, macOS = 미서명 유지.

**실측(2026-07-29, GitHub API 무인증 접근):**

| 리포 | 응답 | 상태 |
|---|---|---|
| `Vinclums/Vinc` | **404** | **비공개** |
| `Vinclums/Vinc-homepage` | 404 | 비공개 |
| `Vinclums/Vincs-app` | 200 | 공개(릴리스 호스트) |

소스 리포가 비공개다. **SignPath Foundation 은 공개 OSS 리포만 지원**하므로 D44 의 $0
경로는 현 상태로 성립하지 않는다. 문서 간 진술도 충돌한다 — `release.yml:10` 은
"소스 레포는 비공개"(정확), `DIAGNOSTICS-macos-2026-07.md:117` 은 "리포 공개 상태가
SignPath 자격의 전제"(경고는 맞으나 현 상태 미반영).

**대안 조사 결과 — Azure Trusted Signing(현 Artifact Signing)은 자격 미달:**
월 $9.99(Basic, 5,000 서명)로 가장 저렴한 축이지만, **미국·캐나다 개인 또는 EU·영국
조직**만 등록 가능하다. 한국 개인·조직은 해당 없음.

**남은 선택지 3개(발주자 결정 사항):**

| 안 | 비용 | 전제 | 부작용 |
|---|---|---|---|
| **A. 리포 public 전환 → SignPath Foundation** | $0 | 히스토리 시크릿 감사(D44 당시 "키·`.env` 커밋 0건" 확인 이력 있음) | 소스 전면 공개. **부수 이득: macOS 러너 10배 과금 해소**(§4.3) |
| **B. 미서명 유지(현상)** | $0 | 없음 | Windows SmartScreen·macOS Gatekeeper 경고 지속. **다운로드 페이지 카피와 모순**(§1.4) |
| **C. 유료 OV/EV 인증서** | ~$200~350/yr | 조직 실재 검증 | 갱신 관리 부담, macOS 는 별도 $99/yr |

> **권고**: A 를 우선 검토. D44 가 원래 의도한 경로이고 CI 비용까지 같이 해소된다. 다만
> "소스 전면 공개"는 사업 판단이라 기술만으로 결정할 수 없다 — 공개가 불가하면 **B 를
> 명시적으로 재확정**하고 §1.4 의 카피 모순을 정리하는 편이 낫다(현재는 "곧 서명한다"고
> 약속만 하고 방치된 상태).

> ### ✅ 결정됨 — **B, v1.0.0 까지** (발주자 2026-07-30)
>
> 위 권고 중 후자를 택했다. 소스 전면 공개는 되돌릴 수 없고, 서명 하나를 위해 1.0.0 전에
> 감행할 사안이 아니라는 판단이다. **D44 는 이 결정으로 대체된다.**
>
> 기한 없는 보류가 아니라 **v1.0.0 재검토**가 박힌 결정이라는 점이 중요하다 — §1.4 가
> 지적한 카피 모순도 이로써 해소된다. 다운로드 페이지의 `winFoot`("서명된 빌드는 후속
> 마일스톤에서 제공됩니다")이 **뒤에 실제 결정이 없어서** 모순이었던 것이고, 이제 있다.
> 카피는 고치지 않는다(버전 번호를 공개 약속에 박지 않는다).
>
> 정본: `DEPLOYMENT.md` §1.7. 1.0.0 재검토 시 확인할 3가지도 거기 적었다.

### 1.2 ⚠ 서명 키 — 이 파이프라인의 단일 실패점 1순위

**키를 잃으면 복구 경로가 없다.** `release.yml:13-16` 이 명시하듯 공개키는
`tauri.conf.json` 에 박혀 있고, 클라이언트가 서명 불일치 번들을 거부한다. 새 키로 바꾸면
그 pubkey 는 **새 설치본에만** 들어가므로 **이미 배포된 전 사용자가 자동 업데이트에서
영구 이탈**하고 수동 재설치 외에 길이 없다.

**현 상태(실측):**
- 백업·복구·회전 절차 **문서 0건**(전 리포 검색)
- 실제 키 파일이 워크스페이스 루트에 평문 배치:
  `vinc-updater-signing.key`(348B) · `.key.pub`(152B) — `.pub` 내용이 `tauri.conf.json:34`
  의 pubkey 와 바이트 일치 확인
- ✅ 세 리포 어디에도 **커밋되지 않음**(리포 바깥 상위 디렉토리)
- ✅ 개인키는 암호화됨(`rsign encrypted secret key` 헤더)
- ⚠ 그러나 `Vinc/.gitignore` 에 `*.key`·`*.pem` 패턴이 **없다** — 누가 리포 안으로 옮기면
  아무것도 막지 않는다
- ⚠ **백업이 이 로컬 파일 하나로 보인다** — 개발 머신이 죽으면 복구 불명

**권고(P0)**: ① 키·암호를 오프사이트에 백업(암호 관리자 또는 봉인 매체) ② 백업 위치와
복구 절차를 `DEPLOYMENT.md` 에 기록 ③ `.gitignore` 에 `*.key`·`*.pem` 추가(1줄)
④ `vinc_key.pem`(삭제된 가비아 VM 의 SSH 키) 폐기.

### 1.3 버전 범프 — 6곳이 아니라 7곳, 그리고 이미 어긋나 있다

**실측 불일치 1건:**

```
Vinc/app/package-lock.json:3   "version": "0.6.0"   ← 7릴리스(0.6.0→0.6.7) 방치
Vinc/app/package.json:4        "version": "0.6.7"
```

원인은 **비대칭**이다 — `Cargo.lock` 은 체크리스트에 있는데 `package-lock.json` 은 빠져
있다. 이 파일은 의존성이 바뀔 때만 갱신되고 버전 범프 때는 아무도 안 만진다. `npm ci` 는
의존성 트리만 대조하므로 **조용히 통과**한다.

**추가로 발견된 문서 소실**: 6곳을 열거한 표가 **현행 `DEPLOYMENT.md` 에서 사라졌다**
(Azure 전면 개정 시 §1 이 "무변경" 으로 축약되며 유실 — 구 개정판 `927db3b^` 에만 존재).
현행 문서만 읽고는 어디를 고쳐야 하는지 알 수 없다.

**`version_info.txt` 는 단일 파일 안에 표기가 3가지**라 자동화 시 가장 취약하다:
`filevers=(0, 6, 7, 0)` / `'0.6.7.0'`(점 4개) / 주석의 `(현재 0.6.7)`.

**권고(P1)**: 범프 스크립트(`scripts/bump-version.py`) 신설 — 7곳을 한 번에 갱신하고
**갱신 후 전 파일이 같은 버전인지 검증**해 불일치면 exit 1. 릴리스 워크플로 초입에 같은
검증을 게이트로 넣으면 태그와 파일이 어긋난 채 빌드되는 일이 원천 차단된다(현재
"업데이트 토스트 무한 반복" 함정의 근본 해소).

### 1.4 릴리스 카드 — 이중 저작 + 키 스킴 4릴리스 후 고갈

릴리스 1건당 **EN(DOM) 24행 + ko(JS 사전) 13행 = 최소 37행**을 손으로 쓴다. 게다가
CHANGELOG(개발자용 한국어)와 릴리스 카드(사용자용 EN 원저 + ko 원저)는 **완전히 다른
3벌의 텍스트**다. 이건 `CHANGELOG.md:3` 이 "사용자 노출 카피 정본은 `site/release/`" 라고
명시한 **의도된 이중 저작**이므로 자동 변환 대상이 아니다 — 자동화하지 말 것.

**단, 키 접두사 스킴은 곧 고갈된다**: `d0`(v0.1.1) → … → `v0`(v0.6.7). 남은 것은
`w0·x0·y0·z0` **4개뿐**이고 그 뒤 규칙이 없다(하한이 `d0` 라 재활용도 불가).

**권고(P2)**: 접두사를 버전 기반(`r067` 같은)으로 전환. 지금 바꾸면 기존 카드는 그대로
두고 신규만 새 스킴을 쓰면 되지만, 고갈된 뒤에는 급하게 정해야 한다.

### 1.5 `mk_alias` — 실패해도 CI 가 초록

```bash
mk_alias() { … [ -n "$m" ] && cp "$m" "up/$t" && echo … || true; }
```

glob(`*_x64-setup.exe`)이 안 맞으면 조용히 건너뛴다. **Tauri 번들 파일명 규칙이 바뀌면
홈페이지 다운로드 버튼 4개가 전부 404 가 되는데 CI 는 초록**이다. 업데이터 서명 누락은
`exit 1` 로 막으면서(같은 파일 174-178행) 별칭 누락은 안 막는 **비대칭**.

**권고(P2)**: 4개 별칭이 전부 생성됐는지 확인하고 하나라도 없으면 exit 1.

## §2 웹 Vinc (`/app/`)

### 2.1 ⚠ 웹과 데스크탑이 같은 버전을 주장한다 — 지금 실제로 어긋나 있다

```
v0.6.7 태그 이후 app/ 소스 14개 파일 변경(D68 Sankey 재작업 포함)
그런데 app/package.json 은 여전히 0.6.7
```

다음 사이트 배포가 돌면 **웹 Vinc = D68 들어간 새 코드**, **데스크탑 v0.6.7 설치본 = 그
이전 코드**인데 **양쪽 `__APP_VERSION__` 이 똑같이 `"0.6.7"`** 이다.

이건 `vite.config.ts` 주석이 밝힌 원래 취지("어느 버전에서 났는지 혼동을 원천 차단",
macOS v0.1.6 리포트 대응)를 **웹 경로에서 정확히 무력화**한다. 진단 리포트가 `v0.6.7`
이라고 해도 어느 빌드인지 판별할 수단이 없다.

**권고(P3)**: 웹 빌드에 git SHA(또는 빌드 시각)를 별도 상수로 주입해 `sidecarDiag` 에
함께 싣는다. 버전 문자열은 그대로 두고 식별자만 덧붙이면 되므로 파급이 작다.

### 2.2 cross-repo 트리거 부재 — paths 필터로는 해결 불가

`app/` 은 `Vinclums/Vinc` 에, 워크플로는 `Vinclums/Vinc-homepage` 에 있다. **cross-repo
push 이벤트는 전달되지 않으므로** `paths` 를 `app/**` 로 넓혀도 트리거되지 않는다.
`repository_dispatch` 또는 Vinc 측에서 `workflow_dispatch` 를 쏘는 배선이 필요하다.
(이 갭 자체는 `DEPLOYMENT.md:346` 에 이미 문서화돼 있다.)

### 2.3 무핀 체크아웃 — site 수정이 미검증 app 코드를 함께 배포한다

```yaml
- uses: actions/checkout@v4
  with:
    repository: Vinclums/Vinc     # ref: 없음 → 항상 기본 브랜치 HEAD
```

`site/` 오탈자 하나만 고쳐 push 해도, 그 시점 Vinc main 의 **미검증 최신 커밋**이 웹
Vinc 로 함께 나간다. site 변경과 app 변경을 커밋 단위로 분리할 수 없는 구조다.

**권고(P3)**: `ref` 를 최신 릴리스 태그로 핀하고(데스크탑과 웹이 같은 코드), app 을 급히
반영해야 할 때만 `workflow_dispatch` 입력으로 ref 를 넘긴다. 2.1(버전 식별자)과 함께 하면
"웹이 지금 어느 코드인지"가 확정된다.

## §3 품질 게이트 — 가장 큰 갭

### 3.1 ⚠ 파이썬 테스트 498건이 CI 에 전혀 없다

`Vinc/tests/` = 파일 **37개**, `def test_` **498개**(CHANGELOG v0.6.7 의 "493건 통과"와
근사). 실행 수단은 `verify.py`(stdlib unittest) 하나.

**CI 배선 실측 = 0건:**
- `release.yml` — 파이썬 테스트 0. 유일한 검증은 사이드카 스모크(`/health=="ok"`) — "빌드가
  실행되나"이지 기능 검증이 아니다
- `hub-deploy.yml` — 테스트 0. `tools/list` grep 은 **배포 후** 확인이라 **배포를 막지
  못한다**
- `scripts/gate_forbidden.py`(카피 보이스 금지어 게이트)도 미배선 — 그걸 잠그는
  `tests/test_gate_forbidden.py` 를 돌리는 CI 가 없다

즉 **owner 격리(SEC-1)·쓰기 테넌시(SEC-3)·동기화 병합 같은 급소 테스트가 전부 사람의
기억에 의존**한다. 이번 세션에서 허브를 컨테이너로 재작성하고 배포까지 했지만, 그 과정에서
498건이 한 번도 돌지 않았다.

**권고(P1, 최우선)**: `Vinc` 에 `ci.yml` 신설 — push/PR 시 `python verify.py` +
`gate_forbidden.py`. `hub-deploy.yml` 은 이 게이트를 `needs:` 로 걸어 **테스트가 깨지면

### 3.2 프론트엔드 — 테스트·lint 전무, typecheck 는 build 안에 접힘

`Vinc/app/package.json` scripts = `dev`·`build`·`preview`·`tauri` 넷.
devDependencies 4개(`@tauri-apps/cli`·`@types/three`·`typescript`·`vite`).

- vitest/jest/playwright **없음** · eslint/prettier/biome **없음**

- 결과: 프론트 타입 오류는 **사이트 배포 워크플로에서만** 잡히고, 데스크탑 릴리스에서는
  tauri-action 내부에 묻힌다

**권고(P2)**: `"typecheck": "tsc --noEmit"` 스크립트 분리 + CI 배선(가장 싼 개선).
테스트 프레임워크 도입은 별건 — 이번 D68 작업처럼 **순수 함수 모듈**(`atlas-lodes.ts`)이

## §4 시크릿·토큰·비용

### 4.1 PAT 2종 — 만료가 태그 push 후에야 드러난다

| PAT | 실패 지점 | 성질 |
|---|---|---|
| `RELEASE_TOKEN` | `release.yml` 3개 잡 | **태그를 이미 push 한 뒤** 실패 → 태그 삭제·재push 없이 재시도 불가 |
| `VINC_REPO_PAT` | `site-deploy.yml` 2번째 스텝 | 사소한 사이트 수정마다 도는 워크플로라 **만료 순간부터 모든 사이트 배포가 막힌다** |

`RELEASE_TOKEN` 에는 추가 함정이 있다 — `gh release create … 2>/dev/null || true`(195행)가
3잡 경쟁 흡수 목적이지만 **토큰 만료 실패도 똑같이 삼킨다**. 다음 `upload` 에서 터지되
에러가 "릴리스 없음"으로 나와 **원인이 토큰임을 감춘다**.

**두 PAT 모두 만료일·소유자·갱신 절차가 어느 문서에도 없다.**

**권고(P4)**: ① 만료일을 `DEPLOYMENT.md` 에 명시 ② 릴리스 워크플로 초입에 토큰 유효성
사전 검사(`gh auth status` 또는 릴리스 목록 1회 조회)를 넣어 **태그 push 전에** 실패시킨다
③ 중장기적으로 GitHub App(만료 없는 설치 토큰)으로 전환 검토.

### 4.2 stale 문서·잔재 (정리 대상)

- `account-ci.yml` 헤더: "배포는 여전히 수동 SSH(deploy-account.sh)" — 이제 CD 가 있다
- `account/deploy/deploy-account.sh`: 대상 VM(가비아)이 삭제됨 — 실행 불가
- `site/download/index.html:251`: "A signed build follows a later milestone" — D44 는 macOS
  를 **무기한 미서명**으로 확정했다. **카피와 결정이 어긋난다**
- `Vinc/pyproject.toml:7`: `version = "0.0.1"` — 릴리스 버전과 무관하게 고정(의도 확인 필요)

### 4.3 비공개 리포의 CI 과금 — public 전환의 부수 이득

GitHub Actions 는 **비공개 리포에서 macOS 러너에 10배 가중치**를 적용한다. 릴리스마다
3-OS 매트릭스가 도는 구조라 이 비용이 누적된다. §1.1 의 A 안(public 전환)은 코드 서명
자격과 **CI 과금을 동시에** 해소한다 — 두 이득을 묶어서 판단할 것.
