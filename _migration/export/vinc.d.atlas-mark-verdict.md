# Atlas 마크 언어 판정과 경쟁 비교

> **지위: 연구 입력(research-input).** 채택은 발주자 결정(DEC)으로만 정본화된다.
> [[vinc.d.atlas-mark-redesign]] 의 제안 M1~M5(DEC 후보 D77~D80)를 판정하고,
> GM-15 를 분석하며, [[vinc.d.atlas-visibility-verification]] 과의 내부 충돌을
> 실 데이터로 정리하고, 경쟁 제품 12종과 8축으로 비교한다.
>
> **적재 주석 (2026-08-03).**
> 1. **GM-14 가 배포된 것으로 관측된다.** 적재 직전 `vinc_search` 가
>    `total_count`·`has_more`·`next_cursor`·`page` 를 반환했고 행에 `truncated: true`
>    가 붙었다. 같은 세션 초반 호출에는 없던 필드다. 0.7.2 T1(커서 페이지네이션 +
>    요약·상세 분리)이 그 사이에 들어간 것으로 보인다. **[세션 내 관측]**
> 2. **DEC 번호 분열이 실물로 확인됐다.** `concept:dec-d75`("D75 Atlas 소멸 정지")와
>    `concept:dec-d76`("D76 Atlas 대비 이중 게이트")가 스토어에 이미 존재하는데,
>    2026-08-02 검증 문서가 같은 결정을 `concept:dec-d-vis-a`·`dec-d-vis-b` 로 중복
>    등록했다. §3.2 에서 다룬다. **[스토어 실측]**
> 3. **코드 앵커는 이번에도 미검증이다.** GitLab 리포에 접근하지 못했다. 원문의
>    `atlas3d.ts:224/249/253`, `query.py:514`, `atlas.ts toL3` 는 전부
>    **[문서 자기보고]** 이며 착수 전 실제 HEAD 대조가 필요하다.
> 4. 반면 노드 타입 분포와 DEC 노드 존재 여부는 `vinc_domains`·`vinc_neighbors` 로
>    직접 쟀다 **[스토어 실측]**. Line2 의 패키지 소속과 색맹 안전 상한은 공식 문서·
>    문헌으로 확인했다 **[웹 확증]**.

## §1 D77~D80 판정

### 1.1 D77 = M1 유리 은퇴 + M4 사문 채널 정리 · 채택 권고

채널 예산 진단 자체는 타당하다. 색상·재질·선폭 세 채널이 비어 있고 형태 하나가
과부하라는 분석은 시각화 문헌과 정합한다(Bertin · Mackinlay 1986 대 2006 · Healey
계열: 형태는 hue·크기·명도보다 약한 명목 채널이고 축소에 먼저 무너진다).

문서 자기보고가 사실이면 다크 기본 테마에서 유리는 렌더조차 되지 않는다. 그렇다면
두 재질 체계를 유지하는 비용만 내고 이득이 0이다. 웹 문헌도 3D 물성·글로우의 정확도
이득을 확인하지 못했다고 일관되게 보고한다(chartjunk 후속 실험 1994·2013·2015).
렌더 이득 없는 코드 경로를 지우는 것은 순수 정리다.

**조건:** 코드 앵커가 미검증이므로 구현 착수 전 실제 HEAD 대조가 선행돼야 한다.
다크에서 유리가 실제로 렌더되고 있다면 "이미 다크는 평면"이라는 전제가 틀리므로
재검토한다. 또한 [[vinc.d.atlas-visibility-verification]] 의 R9(렌더 파이프라인
점검: outputColorSpace·toneMapping·ColorManagement)를 이보다 먼저 돌린다. 확인이
싸고 정상이면 즉시 종료하는 관문이다.

D37 Liquid Glass 를 크롬 층에 유지하는 결정은 옳다. 크롬에서 물성은 데이터 채널이
아니라 UI 어포던스이므로 기회비용 논리가 적용되지 않는다.

### 1.2 D78 = M2 타입=색 · 기각하고 M2′ 로 대체 권고

가장 무거운 안건이다. M2 와 M2′ 를 정면 비교한다.

**M2(색)의 논리는 탄탄하다.** 옵시디언 대비 Vinc 의 구조적 우위는 타입인데 화면이
안 쓴다. VOWL·Bloom·Gephi 관례가 색=타입이다. 반론 처리(닫힌 5색은 브랜드 팔레트
안이라 임의 채색이 아니다, 색맹은 중복 부호화로, 공유팩은 색이 타입에 고정되면
오히려 안정)도 논리적으로 흠이 없다.

**그런데 전제가 실 데이터와 어긋난다.** M2 의 전제는 "5종 타입을 약한 형태 채널이
못 나른다"이고, 이는 5종을 상시 구별해야 할 때만 성립한다. 실측상 상시 존재하는
타입은 3종뿐이다. 3종은 채움(개념) · 외곽선만(레코드) · 이중 외곽선 또는 형태 변화
(에피소드)로 색 없이 상시 구별된다. **즉 M2 는 실 데이터에 존재하지 않는 문제를
풀기 위해 불변식을 깨는 비용을 지불한다.**

색맹 안전 상한도 참고가 된다. 검증된 팔레트(Wong · ColorBrewer qualitative) 기준
카테고리 색 상한은 최대 6색이고, 다채널(색 + 형태·패턴)을 쓰면 8~10 까지 확장된다.
학술 실험은 색 단독 feature-search 용량 상한을 7 미만으로 보고하기도 한다.
즉 3종에 색을 준다면 안전 범위 안이지만, **3종은 색 없이도 충분하므로 색은 있으면
좋은 것이지 없으면 안 되는 것이 아니다.** VOWL 명세도 색으로 클래스·속성을 가르되
색의 부재가 결정적 정보 손실을 뜻하지 않는다고 명문화한다.

**재개 임계(reopening threshold)를 명문화한다.** Bridge·Entity 가 실제로 쓰이기
시작해 상시 노드 타입이 4종을 넘고, 그중 형태·채움 조합으로 못 가르는 쌍이 생기면
D78 을 자동 재상정한다. 그때는 모노크롬이 우위가 아니라 족쇄로 전환된다.

색을 여는 결정 자체는 브랜드·불변식 사안이므로 발주자 몫이다(§5).

### 1.3 D79 = M3 선 폭 복원(Line2) · 채택 권고

**핵심 확인: Line2·LineMaterial·LineGeometry 는 three.js 공식 애드온
(`three/addons/lines/`)이며 three 패키지 배포물에 포함된다. 별도 npm 의존성이
아니다.** three.js 공식 문서가 "Line2 is an addon, and must be imported explicitly"
라고 명시하고 임포트 경로를 `three/addons/lines/Line2.js` 로 안내한다. 따라서
**신규 라이브러리 추가 금지 불변식에 걸리지 않는다.** 이미 보유한 three 에서 가져온다.
**[웹 확증]**

기술 배경도 확증됐다. three.js `LineBasicMaterial.linewidth` 문서가 대부분 플랫폼에서
값과 무관하게 1px 로 고정되며 더 굵은 선이 필요하면 Line2 나 LineSegments2 를 쓰라고
명문화한다. 즉 D33 의 "폭 0" 결정이 "튜브 아니면 1px" 이분법의 산물이었다는 진단이
정확하다.

**선행 의존성을 재배선한다.** 원문은 D78 선행을 걸었으나 M2′ 를 택하면 선폭은 색
결정과 무관해진다. 선폭은 방향·무방향·크로스를 나르는 별개 채널이다.
**D78 → D79 를 D77 → D79 로 바꾼다.**

**주의:** Line2 는 화면 리사이즈마다 `resolution` 갱신이 필요하고, 엣지가 수천 개면
세그먼트 지오메트리 비용이 THREE.Line 보다 크다. 대규모에서는 M5(필터·국소 그래프)와
병행해야 실효가 난다.

### 1.4 D80 = M5 국소 그래프 기본 진입 · 채택 권고

**실은 가장 임팩트가 큰 안건이다.** 옵시디언 실무에서 어떤 규모에서도 쓸모가
유지되는 유일한 뷰가 국소 그래프였고, Bloom·GraphXR·InfraNodus 등 전문 도구는 전부
검색 또는 노드 선택에서 시작하는 진입 모델을 쓴다. **전체 그래프 먼저는 PKM
장난감의 관례이지 전문 도구의 관례가 아니다.**

Vinc 는 이미 L2 국소 그래프와 `vinc_neighbors`(1-hop) · `vinc_graph`(seed+depth)
백엔드를 갖고 있다. 진입 기본값만 바꾸면 되는 저구조 변경이다.

**조건:** "별건 · 사용성 확인 후"라는 원문 판단은 옳다. 3D 전체 조망은 공간 기억·
조망 가치가 있으므로 없애지 말고, **기본 진입만 국소로 바꾸고 전체 조망은 명시적
전환(줌아웃 또는 버튼)으로** 남긴다.

## §2 GM-15 엣지 해석기 상세 분석

### 2.1 merge 의미론 영향 분해

Vinc 의 MERGE 규칙은 노드가 id 정확 매칭이고, 엣지는 **양 끝 노드가 매칭된 뒤**
`(from, type, to)` 정확 매칭이다. 문제의 근원은 "양 끝 노드가 매칭된 뒤"에서 매칭
소스가 payload `nodes` 로 한정된 것이다.

스토어 조회를 넣으면 두 갈래로 갈린다.
- **(a) 엔드포인트의 타입 확인만 스토어에서 한다** → 엣지의 정확 매칭 규칙은 불변이다.
  merge 의미론에 영향이 없다.
- **(b) 조회 결과로 payload 에 없는 노드를 갱신 대상으로 취급한다** → props·tags 보존,
  owner 스탬핑, theme fold 가 개입한다. **이 지점이 위험하다.**

**회피법이 이미 존재한다는 사실이 중요하다.** 기존 노드를 id·type·title·domain 만
최소로 nodes 에 실으면 matched 로 붙고 props·tags 는 보존된다. 즉 스토어 조회의
이득은 정확성이 아니라 편의(payload 를 덜 실어도 됨)다.

### 2.2 타 시스템 선례 [웹 확증]

- **Cypher MERGE:** Neo4j Knowledge Base 가 정확히 같은 함정을 경고한다. 그래프의
  기존 노드·관계를 쓰려면 노드에 먼저 MATCH 또는 MERGE 하고, 바인딩된 변수로 패턴을
  MERGE 하라고 지시한다. 전체 패턴을 한 번에 MERGE 하면 패턴 전체가 매칭되거나
  전체가 생성되며, 불균형이 있으면 중복 요소가 만들어진다고 명시한다. 즉
  **엔드포인트를 먼저 바인딩하라가 표준**이며, Vinc 의 "nodes 에 최소 형태로 실어라"
  회피법이 바로 이 관례의 Vinc 판이다.
- **RDF/SPARQL:** `INSERT DATA` 는 ground triple 만 넣고 엔드포인트 존재를 강제하지
  않는다(dangling reference 허용, 스키마리스). 반대 극단이다. Vinc 는 타입 라벨이
  붙는 property graph 라 이 모델을 그대로 못 쓴다.
- **결론:** property graph 계열(Cypher · TinkerPop · GraphQL 뮤테이션)의 표준은
  "엔드포인트를 먼저 확정, 없으면 명시적 실패 또는 명시적 생성"이지 조용한 skip 이
  아니다.

### 2.3 MCP 도구 설계 관점 [웹 확증]

조용한 skip 은 명백한 안티패턴이다. MCP 도구 설계 지침은 두 안티패턴을 함께
지목한다: **오류를 조용히 억누르는 것(빈 결과를 성공으로 반환)** 과 **단일 실패로
전체 워크플로를 종료하는 것.** 둘 다 코디네이터(호스트 LLM)가 눈을 가린 채 판단하게
만든다. 부분 성공은 무엇이 성공했고 무엇이 왜 실패했는지를 명시해야 한다.

접근 실패와 정당한 빈 결과를 구분하라는 지침도 그대로 적용된다. "대상 노드가 payload
에 없어 타입 미상(`?`)"과 "타입이 정말 안 맞음"은 다른 오류이고, 0.7.2 T4 의 값싼
수정이 이미 이 둘을 구분하기로 한 것은 옳은 방향이다.

### 2.4 채택 권고와 중단 기준

**권고: 제한된 GM-15 채택.** "스토어 조회로 엔드포인트 타입만 확인하고, 노드 생성·
갱신은 하지 않는다." 조회로 확인된 기존 노드로 향하는 엣지는 matched 로 붙이되,
그 노드의 props·tags·title·domain 은 건드리지 않는다(payload 에 없으므로 갱신 의도
없음으로 간주). 이렇게 하면 merge 의미론은 불변이고 조용한 skip 만 사라진다.

**partial 보고 강화:** 응답 `warnings` 에 skip 대신 `resolved_from_store` 카운트를
넣고, 여전히 미해결인 엔드포인트는 명시적 오류로 남긴다.

**중단 기준 셋.**
1. 스토어 조회가 대량 ingest 에서 노드당 1회 조회로 배치 지연을 2배 초과로 떨어뜨리면
   배치 사전 조회(id 집합 일괄 조회)로 전환하거나 롤백한다.
2. 조회가 owner 스코프를 넘는 노드를 긁어오는 보안 회귀가 생기면 즉시 중단한다
   (owner 격리가 상위 불변식).
3. 조회 확인 노드에 props 갱신이 발생하는 정황이 테스트에서 잡히면 중단한다(경계 위반).

## §3 내부 충돌 정리

### 3.1 마크 재설계 대 가시성 검증 · 실 데이터로 판정

[[vinc.d.atlas-visibility-verification]] §5 는 "노드 5종 + 엣지 6종을 상시 모노크롬으로
구별하는 것은 과부하 → 상시 전부 구별 포기, on-demand 전환, 상시엔 형태 3종 + 크기만"
이라 결론지었다(모노크롬 유지, 구별 포기). D78 은 "모노크롬 재정의, 색 열기"로 구별을
되찾는다. 정반대 처방이다.

**판정 셋.**
1. **검증 문서 §5 의 "5종 + 6종" 전제는 노드에 관한 한 틀렸다.** 상시 노드는 3종뿐이고
   Bridge·Entity 는 0이다. 엣지 6종의 실제 분포는 이번에 집계하지 못해 **[미확인]**
   이나, 노드에 관한 한 5종 과부하는 실 데이터에 없는 문제다.
2. **따라서 §5 의 처방(상시 구별 포기)은 과잉 대응이다.** 3종은 형태·채움으로 상시
   구별되므로 포기할 필요가 없다. "형태 4종으론 1종이 모자라다"는 계산 자체가 실
   데이터에선 성립하지 않는다.
3. **그러나 D78(색)도 과잉이다.** 3종이면 색까지 갈 필요가 없다.

**두 문서는 합쳐진다. 통합 해법:**
- **상시 화면:** 노드 3종을 형태 + 채움으로 구별한다(개념 = 채움, 레코드 = 외곽선만,
  에피소드 = 형태 변화 또는 이중 외곽선). 크기는 연결수. 색 없음(모노크롬 유지).
- **엣지:** 방향(화살표·테이퍼) + 선폭(D79 Line2)으로 방향·무방향·크로스를 구별한다.
  파선은 크로스 전용.
- **on-demand:** Bridge·Entity 가 등장하거나 세부 타입·evidence·confidence 를 볼 때는
  hover·필터·범례 토글로 드러낸다(검증 문서 §5 의 옳은 부분).

즉 **"3종은 상시 구별(모노크롬 유지), 나머지·세부는 on-demand"** 가 두 문서의
교집합이며 D78 의 색 열기보다 우월하다.

### 3.2 DEC 번호 분열 · 정리 필요

**번호 체계가 실제로 갈라졌다. [스토어 실측]**

| 결정 내용 | 정수 DEC(기존) | 문자 DEC(검증 문서가 추가) |
|---|---|---|
| fog 적응 + recede 정본 준수 | `dec-d75` Atlas 소멸 정지 | `dec-d-vis-a` |
| 마크·엣지 사다리 + 대비 게이트 | `dec-d76` Atlas 대비 이중 게이트 | `dec-d-vis-b` |
| 라벨 가독성 + 사용자 조절권 | 없음 | `dec-d-vis-c` |
| 준의미 줌 · 형태 · 집계 | 없음 | `dec-d-vis-d` |
| 렌더 파이프라인 점검(R9) | 없음 | `dec-d-vis-0` |

마크 재설계는 다시 정수 시퀀스(D77~D80)로 돌아왔다. 결과적으로 같은 주제가 세 규약에
흩어져 있다.

**권고.** GRAPH.md 관례상 DEC 는 `concept:dec-{id}` 이고 정수 시퀀스가 주 규약이므로
정수로 통일한다. `dec-d-vis-a` 와 `dec-d-vis-b` 는 각각 `dec-d75`·`dec-d76` 과 동일
결정이므로 구 개념에 `superseded` 태그를 달고 대체 record 를 붙인다(관례 §노드 종류).
정수 번호가 없는 `dec-d-vis-0`·`c`·`d` 는 새 정수 번호로 승격해야 하는데, **번호
부여는 거버넌스 행위이므로 이 문서에서 하지 않는다.** 발주자 결정 사항으로 올린다.

### 4.1 뼈아픈 지점

**뒤처진 것 셋.**
1. **진입 모델이 옛날 관례다.** 전문 도구는 전부 검색·노드 진입인데 Vinc 는 전체
   그래프 먼저다. 이건 옵시디언이 욕먹는 바로 그 지점이다. D80 이 이걸 고치는
   안건인데 아직 검토에 머물러 있다.
2. **선폭이 데이터를 안 나른다.** Gephi·Cytoscape 는 오래전부터 선폭·선농도·선스타일로
   weight 와 관계 종류를 나른다. Cytoscape 는 파선과 실선으로 관계 타입을 가른다.
   Vinc 의 3D 엣지는 폭 0 · 농도 사문으로 2비트만 나른다. D79 가 고친다.
3. **운영 메타데이터를 화면에 안 싣는다.** Vinc 는 evidence·confidence 를 **데이터로는
   갖고 있으면서** 화면에 안 쓴다. Bloom 은 룰 기반으로 속성을 색·크기·캡션에 싣는다.
   **옵시디언보다 나은 데이터 모델을 옵시디언 수준으로 보여주는 낭비다.**

**남들이 이미 푼 문제를 다시 푸는 것 둘.**
4. **hairball 은 답이 나와 있다.** 국소 그래프 + 필터 + 검색 진입. Vinc 는 이걸
   "채널로 풀까 상호작용으로 풀까"로 두 문서에서 논쟁 중인데 업계는 상호작용으로
   끝냈다. M5 가 옳게 그 결론에 도달했다.
5. **색=타입 논쟁도 답이 있다.** 색은 쓰되 중복 부호화로. 단 Vinc 의 특수성(공유팩
   결정론·모노크롬 브랜드)이 있어 그대로 복붙하면 안 된다. 그래서 M2′ 가 Vinc 엔 맞다.

## §5 반드시 지켜야 할 강점 · 냉정 판정

**진짜 우위(보존 최우선).**
- **완전 오프라인 · 무클라우드 · 데이터 소유 + 결정론 백엔드.** Vinc 의 유일무이한
  해자다. Bloom(클라우드·유료) · InfraNodus(호스팅) · Kumu(클라우드)와 대비된다.
  Cosmograph·GraphXR·Gephi·Logseq 은 로컬 가능하지만 "결정론 백엔드 + 로컬 임베딩 +
  외부 키 0"을 **전부** 만족하는 제품은 드물다. 재설계 중 외부 폰트·CDN·GPU 라이브러리·
  런타임 LLM 을 슬쩍 들이는 유혹을 **명시적으로 거부**해야 한다. Line2 가 three 내장
  이라 안전한 것도 이 원칙 덕에 확인한 것이다.
- **Chunk=SSoT 무손실 정본.** GraphRAG 류가 LLM 요약으로 원문을 손실하는 것과 정반대다.
  evidence 엣지가 이 청크에 연결돼 원문 추적이 무손실인 것이 핵심이다.
- **3D 폭발 배치의 공간 기억.** 3D 는 판독 정확도 우위는 없으나(문헌 확증) 조망·공간
  기억 가치가 있고 이를 명시 목적으로 두면 근거가 있다. **D80 이 국소를 기본으로 해도
  3D 전체 조망은 선택 모드로 남겨야 한다. 없애지 말 것.**

**잠재적 우위(아직 제품 우위 아님).**
- **타입 엣지의 evidence + confidence.** 옵시디언·Logseq 대비 구조적 우위다. 그러나
  **현재는 화면에 안 나오므로 잠재적 우위다.** 화면화 전까지는 데이터 모델 우위이지
  제품 우위가 아니다. 냉정하게 그렇다.

**조건부 우위.**
- **모노크롬 색비의존.** 색맹·인쇄·공유팩 결정론에 유리한 건 사실이다. 그러나 구별을
  못 하게 만드는 방향으로 작동하면 우위가 아니라 족쇄다. 3종은 형태·채움으로 구별
  가능하므로 지금은 우위로 유지된다. **Bridge·Entity 가 늘어 4종 이상이 상시화되면
  족쇄로 전환된다.** 그 임계가 D78 재개 임계다.

**우위 아님(냉정).**
- **owner 스코프.** 멀티테넌트 격리는 좋은 보안 설계이나 경쟁 제품도 다 갖는다.
  차별점이 아니다. 보안 불변식으로 지키되 강점으로 내세우지 말 것.
- **GRAPH.md 관례 채널.** 호스트에게 관례를 주입하는 것은 영리하나 MCP 도구 description
  관례의 응용이지 Vinc 만의 것이 아니다. 게다가 GM-15 함정이 보여주듯 관례만 따르면
  함정에 걸리는 상태라 아직 미성숙하다. 우위 후보에서 뺀다.

## §8 발주자 결정 필요

1. **D78 타입=색** — 모노크롬 규율(D20·D39) 재정의 요구. 이 문서 판정은 "지금은 불필요,
   M2′ 로 대체"이나 색을 여는 것은 브랜드·불변식 결정이므로 발주자 몫이다. 재개 임계를
   명문화해 자동 재상정되게 할 것을 권고한다.
2. **3D 전체 조망의 지위** — D80 이 국소를 기본으로 하면 3D 폭발 배치는 선택 모드로
   강등된다. 3D 를 제품 정체성으로 볼지 조망 보조로 볼지는 발주자 결정이다.
3. **DEC 번호 승격** — `dec-d-vis-0`·`c`·`d` 에 새 정수 번호를 줄지, 준다면 어떤 번호인지.

## §9 한계

- **코드 접근 불가.** 줄 번호·상수 앵커는 전부 문서 자기보고이며 두 원문 모두 미검증을
  자인한다. 구현 착수 전 실제 HEAD 대조가 반드시 선행돼야 한다.
- **엣지 분포 미확인.** 노드 타입 분포는 실측했으나 엣지 6종의 실제 분포는 집계하지
  못했다. "엣지 6종 과부하" 판정은 노드만큼 확실하지 않다.
- **원격 스토어 미확인.** 모든 실측은 로컬 스토어 기준이다. 계정 그래프 분포는 다를 수 있다.
- **Bloom 제품 상태.** Aura 콘솔에서 Explore 로 개명·통합된 것은 확정이나, 독립 Bloom
  도구의 정식 단종 공지는 확인되지 않았다. 버전 번호 체계가 문서마다 어긋난다.
- **WebVOWL 유지보수.** 원저장소는 2023-07 이후 공개 커밋이 없어 사실상 동면이고 활성
  개발은 제3자 포크로만 이어진다.
- **3D·번들링 문헌은 일반 그래프 대상.** Vinc 특유의 지식 그래프·사용자층에 대한 자체
  사용성 확인 전까지는 추정이다.
