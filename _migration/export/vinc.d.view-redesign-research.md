# 2D 관점·합계 생키 재설계 가능성 분석

> **지위: 연구 입력(research-input).** 발주자 질문 2건(2026-07-25)에 대한 사실
> 기반 판정이다. ① "현 2D는 3D를 평면에 둔 것뿐인데 영상과 유사한 구조로 완전히
> 재설계 가능한가" ② "생키도 지금 방식이 아닌 [bklit 문서에] 나와 있는 구조로
> 가능한가". 근거는 (a) 업로드 영상 21프레임 계측 (b) bklit 문서 원문 fetch
> (c) 라이브 코드 전수 추적. 채택은 §9 DEC 후보 확정으로만.
> 관련: [[vinc.d.motion-research]](모션·툴팁·부록 3 스코프), [[vinc.d.graph-views]](정본).

## 0. 결론 (3줄)

1. **2D 재설계 — 가능하다. 그리고 발주자 진단이 코드와 정확히 일치한다.** 현 2D 는
   설계가 아니라 렌더러 플래그 하나(`flat`)로 만든 **투영**이다. 더 나쁜 것은
   2D 의 세로 위치가 3D 깊이(z)를 0.55 섞은 **잔상**이라 아무 의미도 인코딩하지
   않는다는 점이다(§2). 레퍼런스의 뼈대는 이식 가능하나, **색채·발광은 채택 불가**다
   (§5 색상 검증기 실측 FAIL · D31 닫힌 층).
2. **생키 재설계 — 가능하고, 사실 "복귀"다.** 현행 합계는 **생키가 아니라 누적
   막대**다(§3). 정본 [[vinc.d.graph-views]] §2.3 은 이미 3열 생키를 규정하고 있고
   시안은 열 합계 보존까지 검증을 마쳤다. 즉 새 제안이 아니라 **스펙 미준수 수리**이며,
   bklit 파라미터는 Vinc 의 3열 구조와 **데이터 변환 없이 동형**이다(§4).
3. **레퍼런스는 실제 제품이 아니라 디자인 컨셉 영상이다**(fuselab creative 워터마크).
   따라서 구조·인터랙션 문법은 참고하되 **성능·데이터 규모 근거로는 쓸 수 없다**.
   이 구분이 §7 채택/기각표의 기준이다.

## 1. 레퍼런스 해부 — 영상 21프레임 계측

원본: 21.07초 · 1600×1200 · 30fps · h264. 초당 1프레임 추출 후 전수 판독.
제품명 "Control AI Policy Platform", 제작 워터마크 `fuselab creative`(f_15 이후 노출).
**컨셉 데모** 판정 근거: 워터마크 + 데이터가 시연용 반복값(같은 "Bank of New Yo…"
항목 12회 반복, f_18) + 지표가 프레임마다 튐(Compliance 7% → 63% → 98%).

### 1.1 화면 3종

| # | 프레임 | 화면 | 구성 |
|---|---|---|---|
| A | f_04–f_10 | **2D 지식 지도** | 좌측 세로 **연도 축**(2016–2024, 활성 연도 알약 `2020`, 점선 눈금 리본) · 중심 허브(Constitution) 방사 · 주제 노드 10종 · 좌하단 LEGEND · 하단 지표바 4종 · "Ask a question" 에이전트 입력 |
| B | f_12–f_13 | **단일 노드 포커스** | 그래프 전체 소거 후 노드 1개 + 큰 제목 · 노드 주위 **이퀄라이저 링** · `GAPS 12` 배지 · 감성 막대(엄지 + 게이지) |
| C | f_13→f_15→f_18→f_20 | **팬(fan) 드릴다운** | 노드 → 베지어 5줄 → **카테고리 카드 5장**(18 Services · 3 Entities · 24 Related Federal Laws · 32 KPIs · 12 …) → 카드 선택 시 **잎 20+개로 재팬** · 우측 글래스 상세 패널 |

### 1.2 계측된 시각 문법

- **노드**: 3D 렌더링된 구체. 타입별 색 5종(금=Constitution · 분홍=Entities ·
  보라=Legislation · 초록=Services · 주황=Regulations). 크기 = 중요도.
- **엣지 2종**: 굵은 **발광 빔**(주요 관계, 흰금 그라디언트 + 블룸) / 얇은 **점선**(보조).
- **배지**: 라벨 아래 퍼센트(47%·31%·24%…), 위성 노드에 정수 카운트(8·13·21…).
- **축**: 좌측 연도 축은 **스크러버**로 보이며(활성 연도만 알약으로 강조), 노드
  세로 위치가 연도와 정합하는지는 프레임상 **확정 불가**(f_04 와 f_06 에서 같은
  노드의 세로 위치가 축 눈금과 어긋난다 → **장식 축일 가능성**이 있다).
- **팬 애니메이션**(f_13 포착): 베지어 곡선 위를 **빛 입자가 이동**하며 카드가
  순차 등장. bklit 생키의 `stroke-dashoffset` 성장과 같은 계열 문법.
- **상세 패널**(f_20): Sentiment Rate 45% + 도트 스파크라인 + KPI 타일 4장.

### 1.3 Vinc 와의 구조 대응 — 이미 1:1 이다

| 레퍼런스 | Vinc 현행 | 판정 |
|---|---|---|
| 화면 A 2D 지도 | L0/L1 Atlas | 대응 |
| 화면 B 노드 포커스 | L2(`#atlas/trace/<id>`) | 대응 |
| 화면 C 카테고리 팬 → 잎 | 상세 패널 + D45-V2 드릴다운 | **표현만 다름**(패널 목록 vs 팬) |
| 좌측 연도 축 | timeline 관점 | 관점 축으로 분리돼 있음 |
| 하단 지표바 | 없음 | 신규 여지 |

즉 레퍼런스가 하나의 화면에 겹쳐 놓은 것을 Vinc 는 **관점 축으로 분리**해 놓았다.
이 차이가 §5 판정의 핵심 변수다.

## 2. 현행 2D as-built — "설계가 아니라 투영"이 맞다

`Vinc/app/src/surfaces/atlas3d.ts` 전수 추적 결과, 2D 는 3D 씬 그대로에 플래그
하나를 꽂은 것이다.

| 행 | 코드 | 효과 |
|---|---|---|
| 202 | `const flat = prefs.view === "2d"` | 단일 플래그 |
| 215 | `pz = flat ? 0 : (n.z)*S` | z 제거 |
| **214** | `py = ((n.y) + (n.z)*0.55) * S` | **z 를 y 에 0.55 섞음** |
| 272 | `controls.enableRotate = !flat` | 회전만 잠금(팬·줌 유지) |
| 261 | `scene.fog = flat ? null : Fog(...)` | 안개 제거 |
| 136·176·193 | `if (prefs.view === "2d") … rotation.x = π/2`, `r *= 0.7` | 프리미티브를 카메라로 눕히고 축소 |
| 311 | `cameraPosition({x:n.fx, y:n.fy, z:d*2.2}, …, 700)` | 정면 카메라 |

**치명적 귀결(214행)**: 2D 의 세로 위치는 시간도, 위계도, 중요도도 아니다.
사이드카가 3D 배치용으로 낸 y 와 z 를 섞은 **깊이의 잔상**이다. 레퍼런스가 세로를
연도로 쓰는 것과 정확히 반대 — "2D 인데 세로가 아무 뜻이 없다"가 현 상태의 정의다.

좌표 소유권은 사이드카에 있다(D17). `layout_positions`(query.py:931)가 도메인
클러스터를 **xy 단위원**에 놓고 클러스터 내부를 프리셋 5종으로 편다 — 이 배치는
3D 구면 관람을 전제로 설계됐고, 2D 전용 규칙은 **하나도 없다**.

## 3. 현행 합계 as-built — 생키가 아니라 누적 막대다

`atlas-planar.ts:492–575` `mountTotals` 전수 판독.

| 사실 | 근거 |
|---|---|
| 행 = 도메인, 행마다 트랙 + 3구간 **사각형** | 545행 `<rect class="pl-track">` · 532행 `<rect class="pl-seg pl-s${si}">` |
| **`<path>`·리본·노드 열이 없다** | 파일 내 생키 경로 생성 코드 부재 |
| 구간 구분 = 잉크 농도 3단 | `app.css:388–390` `.pl-s0{.82} .pl-s1{.5} .pl-s2{.26}` |
| 치수 | 행 높이 34px · 막대 16px · 좌라벨 132px · 우합계 56px |
| 묶음 축 1개뿐 | `KEYS` = `origin` 3종 **또는** `connected/gateway/orphan` 3종 (택1) |

**정본과의 간극**: [[vinc.d.graph-views]] §2.3 은 "**3열 생키** — 유입원 → 도메인 →
연결 상태 … 열마다 합계가 같아야 한다(16=16)"를 규정한다. §6 시안 검증표에는
"합계 보존: 유입 16 = 유출 16, 도메인별 in/out 불일치 0"이 **이미 PASS** 로 기록돼
있다(`DESIGN/gallery/atlas-views.html`). 즉 **시안은 진짜 생키였고 앱만 누적 막대로
축약됐다.** 현행 구현은 `origin` 과 `state` 를 동시에 볼 수 없어서(택1 토글) 생키의
본질인 "유입원 → 도메인 → 상태"의 **경로 추적이 원리적으로 불가능**하다.

이것은 부록 3(L0=전량)에 이어 **스펙 미준수 2건째**다.

## 4. bklit 생키 규격 — Vinc 3열과 데이터 변환 없이 동형

문서 원문 fetch 실측값.

| 항목 | 값 |
|---|---|
| 데이터 | `nodes[{name, category: "source"｜"landing"｜"outcome"}]` + `links[{source: idx, target: idx, value}]` |
| 여백 | `{top 40, right 180, bottom 40, left 180}` |
| 노드 | `nodeWidth 16` · `nodePadding 24` · `lineCap 4`(모서리 반경) |
| 비율·시간 | `aspectRatio "2 / 1"` · `animationDuration 1100` |
| 불투명도 | 노드 `fadedOpacity 0.4` · 링크 `strokeOpacity 0.7` / `fadedOpacity 0.1` |
| 그라디언트 | `useGradient true`(소스→타깃) |
| 애니 | 0–600ms 노드 stagger · 200–1100ms 링크 stagger · `cubic-bezier(0.85,0,0.15,1)` |

**핵심 발견**: bklit 의 `category` 3열(`source`→`landing`→`outcome`)은 Vinc 정본의
**유입원 → 도메인 → 연결 상태**와 **정확히 같은 형태**다. `/ledger` 행 하나가
(origin 3종 카운트 + domain + state 3종 카운트)를 이미 싣고 있으므로, 열 노드와
링크는 **순수 폴드 한 번**으로 나온다. 백엔드 변경 0.

Vinc 적용 시 조정 2건:
- `useGradient` **기각** → 단일 잉크 + 값 비례 `stroke-opacity`(모노크롬 §5).
- 링크 `fadedOpacity 0.1` → **0.12**(D32-a 확정값). 노드 0.4 는 확정값과 일치.

## 5. 판정 ① — 2D 재설계, 가능하다. 축을 무엇으로 두느냐가 전부다

### 5.1 3안 비교

| 안 | 세로(y) | 가로(x) | 선행 작업 | 문제 |
|---|---|---|---|---|
| **A. 시간 앵커** | **시간**(`ts`) | 도메인·위상 | 사이드카 프리셋 1개 추가 | **timeline 관점과 중복** — 이미 y=시간이다 |
| **B. 위상 앵커** | 랭크(DAG) | 도메인 | 프리셋 1개 추가 | **flow 관점과 중복** — 이미 랭크다 |
| **C. 축 없음 + 문법 이식**(권장) | 허브 방사 | 허브 방사 | 렌더러 승격 | 레퍼런스의 "연도 축"을 포기 |

**권장 C안의 근거**: 레퍼런스의 2D 가 실제로 잘 읽히는 이유는 연도 축이 아니다
(§1.2 — 축과 노드 위치의 정합조차 확정 불가). 읽히게 만드는 것은 아래 4개다.

1. **허브 중심 방사** — 위성이 허브에 딸린 것으로 즉시 보인다. Vinc D32(허브 승격
   서열 pin>degree)가 이미 규정한 구조이며, `radial` 프리셋이 이미 있다.
2. **노드 위 수치 배지** — 라벨만 있는 현행과 달리 "얼마나"가 마크에 붙어 있다.
3. **라벨 상시 노출** — 현행 기본값은 `labels: "hover"`(atlas-prefs.ts:34). 레퍼런스는
   주요 노드 라벨이 항상 켜져 있다.
4. **하단 지표바** — 지도를 보면서 전체 수치를 잃지 않는다.

이 4개는 **축 없이 성립**하고 Vinc 의 닫힌 층을 하나도 건드리지 않는다.
시간축이 필요하면 관점을 timeline 으로 바꾸면 된다 — **관점 축이 이미 그 역할이다.**

A안은 폐기가 아니라 **레이아웃 프리셋 6번째**(`temporal`)로 남긴다. 프리셋은 열린
층(D31)이라 사용자 선택이고, `_CLUSTER_LAYOUTS`(query.py:926)에 순수 함수 1개를
등록하는 것이 전부다 — D17 결정론 계약도 그대로다.

### 5.2 렌더러 선택

| 후보 | 현황 | 판정 |
|---|---|---|
| 3d-force-graph(현행 flat) | 3D 전용 설계에 얹혀 있음 | 2D 를 계속 세입자로 두는 한 §2 문제는 안 사라진다 |
| **sigma 3.0.3 + graphology**(권장) | **이미 의존성이며 Compare 뷰에서 실사용 중**(atlas.ts:2) | WebGL 이라 수천 노드 견딤. E4(로드맵)가 지목한 바로 그 스택 |
| 순수 SVG(atlas-planar 계열) | 평면 3종이 사용 | 배지·카드 장식은 쉬우나 규모에 약함 |

**권장: sigma 로 승격.** 배지·지표바 같은 DOM 장식은 sigma 캔버스 **위 오버레이**로
얹는다(교체 예정인 자체 툴팁과 같은 층에서 관리 — [[vinc.d.motion-research]] §4-5).
이러면 2D 는 3D 의 그림자가 아니라 **독립 관점**이 되고, 214행 잔상 문제가 소멸한다.

### 5.3 비용

- 사이드카: **0**(좌표는 이미 xy 를 준다. `temporal` 프리셋 채택 시에만 순수 함수 1개)
- 앱: 신규 `atlas2d.ts`(sigma 렌더러) + 배지 오버레이 + 지표바. `atlas3d.ts` 의 flat
  분기 7개 제거 → 3D 코드가 오히려 단순해진다.
- 리스크: Compare 뷰가 이미 sigma 를 쓰므로 **테마·마크 규약을 공유**해야 한다
  (지금은 Compare 만의 스타일). 공유 지점을 먼저 뽑는 것이 순서.

## 6. 판정 ② — 생키 재설계, 가능하다. 그리고 스펙 복귀다

### 6.1 왜 쉬운가

- **데이터**: `/ledger` 행이 이미 3열 정보를 전부 싣는다(`episodic`·`record`·
  `unsourced` / `domain` / `connected`·`gateway`·`orphan`). 사이드카 변경 **0**.
- **보존 검증**: §6 시안이 이미 "개념 단위에서 파생시켜 접는다"로 해결했고
  사이드카 `/ledger` 폴드도 같은 구조다(정본 §6 말미). 열 합계 보존은 **이미 성립**.
- **레이아웃**: d3-sankey·visx 를 **넣을 필요가 없다**. 3열 고정이므로 직접 계산이
  더 짧다.
  - 열 x 3등분 · 노드 높이 = value 비례 · `nodePadding 24` · `nodeWidth 16`
  - 리본 = `M x0,y0 C mx,y0 mx,y1 x1,y1` 양끝 수직 접선 베지어, 두께 = value
  - d3-sankey 의 실제 가치는 다열·순환 그래프의 **정렬 최적화**인데 3열에는 불필요
- **드릴다운**: 리본·노드 클릭 → **기존 `openDrilldown`(D45-V2 3단계) 그대로 재사용**.
  현행 구간 rect 클릭과 계약이 같다(`data-dom`·`data-seg`).
- **애니**: bklit 타임라인 이식하되 총 700–800ms 로 압축([[vinc.d.motion-research]] §4-4).

### 6.2 비용과 함정

- 비용: `mountTotals` 재작성(1파일 국소, 현재 84행). 백엔드 0. 신규 의존성 0.
- 함정 1: `unlinked: "hide"` 시 고아 열이 사라져 **보존이 재계산**돼야 한다
  (시안이 "13 = 13 으로 재계산"으로 이미 검증한 지점).
- 함정 2: 중간 열(도메인) 라벨이 리본 위를 지난다 → 정본 §2.3 이 지시한 대로
  **판(plate) 폭은 `getBBox()` 실측**(추정 금지 · §6 실패 사례 1).
- 함정 3: 숨은 탭에서 `getBBox()` 는 0 을 반환한다 → **보일 때 그리는 지연 빌드**.

### 6.3 얻는 것

지금은 "출처별" 또는 "상태별" 중 하나만 본다. 3열 생키가 되면 **"에피소드에서
유래한 개념이 어느 주제에 쌓였고 그중 몇이 고아인가"** 가 한 화면에서 경로로
읽힌다. 이것이 정본이 §2.3 에서 "운영 가치 — 고아 리본 클릭이 D32 고아 최소화
2동선의 진입점"이라고 쓴 그 동선이며, 현행 누적 막대로는 **원리적으로 불가능**하다.
