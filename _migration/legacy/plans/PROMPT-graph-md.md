## 역할

너는 지식그래프 온톨로지와 에이전트 도구 설계를 함께 다루는 연구자다. Vinc 를 위한
**`GRAPH.md` 규격**을 설계할 근거를 모으고 실행 가능한 권고안을 낸다. 코드를 쓰지 말고
설계 판단의 재료를 만든다.

작업 루트: `D:/Projects/AIProjects/vinc-project` (하위 `Vinc`, `Vinc-docs`, `Vinc-homepage`, `Vinc-design`)

## 반드시 지킬 규율

- **측정하고 말하라.** 추측을 사실처럼 쓰지 마라. 각 주장에 `실측` / `코드근거(file:line)` /
  `출처확인(URL)` / `추정` 중 하나를 붙인다. `추정`에는 "무엇을 재면 확정되는가"를 함께 적는다.
- **근거 없는 안심 금지.** "아마 괜찮다"는 결론이 아니다. 모르면 모른다고 하라.
- **발주자 대신 결정하지 마라.** 비용·위험이 갈리는 지점(§열린 질문 Q3·Q4)은 선택지와
  트레이드오프를 제시하고 질문 형태로 분리한다. 기술적으로 자명한 것만 네가 정한다.
- 이 단계는 **설계 전용**이다. 코드를 고치지 마라. 조사용 스크립트는 스크래치패드에만 쓴다.
- **선행 사례는 실제로 열어 보고 인용하라.** 기억으로 쓰지 마라. 못 열면 "못 봤다"고 적는다.
- `.venv/`, `node_modules/` 는 검색에서 제외.

## 문제

Vinc 는 로컬 우선 지식그래프다. 사용자의 문서를 보관하고, 개념과 개념 사이의 관계를 그래프로
함께 들고 있으며, MCP 로 붙은 AI 어시스턴트가 그것을 읽고 쓴다.

핵심 설계 원칙: **의미 판단은 전부 어시스턴트가 한다.** Vinc 는 모델도 API 키도 없고 받은
것을 그대로 저장한다. 스스로 개념을 추출하거나 관계를 추론하지 않는다.

그 결과로 생긴 공백: **어시스턴트에게 이 그래프의 관례를 알려줄 문서가 없다.** 매 세션
처음부터 지어낸다 — 이건 Concept 인가 Episode 인가 Record 인가, 관계는 `relates_to` 인가
`prerequisite_of` 인가, 도메인 이름은 `research` 인가 `리서치` 인가, 새 개념을 만들 때인가
기존 것에 붙일 때인가(= 입도).

증상: 같은 자료를 Claude 가 넣은 것과 Cursor 가 넣은 것의 모양이 다르고, 두 달 뒤의 같은
사람도 다르게 넣는다. Vinc 에는 이미 어휘 기구가 있지만(아래) **쓰기 전에 읽을 것이 없어서**,
어시스턴트는 틀렸다는 사실을 응답의 `proposed_types` 로 사후에야 안다.

제안: 사용자가 소유하는 마크다운 파일 `GRAPH.md` 를 어시스턴트가 그래프에 쓰기 **전에**
읽게 한다. CLAUDE.md 가 코딩 관례에 대해 하는 일을, GRAPH.md 가 지식 구조화 관례에 대해 한다.

## 확정 사실 (재검증 불요 · 다만 인용 전 file:line 은 확인할 것)

### 데이터 모델

- **노드 라벨 5종**: `Concept` · `Episode` · `Record` · `Bridge` · `Entity`
  — 코드근거 `Vinc/store/embedded_schema.py:111` (`_TRACKED_LABELS`).
  D45 의 `Chunk` 는 이 추적열에 아직 없다(같은 파일 110행 주석이 추가 예정을 적어 둠).
- **관계 테이블**: `Vinc/store/embedded_schema.py:241` (`_REL_TABLES`) 부터.
  | 테이블 | from → to | 비고 |
  |---|---|---|
  | `PREREQUISITE_OF` · `DERIVES_FROM` · `RELATED_TO` · `INHERITS_FROM` | Concept → Concept | CC 4종 |
  | `CROSSES` | Bridge → Domain | |
  | `CONNECTS{role}` | Bridge → Concept | |
  | `ATTACHES_TO{type}` | Record → Concept | rel 테이블이 타입 고정이라 원 엣지 타입을 `type` 속성에 보존 |
  | `ABOUT` | Episode → Concept | F4 episodic↔semantic 다리 |
  | `TYPED{type}` | Entity → Entity | 사용자 저작 엣지 타입의 집(D11-R2) |
  | `MENTIONS{method}` | Chunk → Concept | 코드근거 `embedded_schema.py:266` — D45 문서 경로 |
- **쓰기 계약(wire)의 엣지 이름**: `relates_to` · `prerequisite_of` · `derives_from` ·
  `inherits_from` · `connects_via` · `about` — 코드근거 `Vinc/api/fragment.py:48` 부터.
- ⚠ **`relates_to` 만 무방향으로 dedupe** 된다(MERGE 전에 역방향 존재를 확인해 접는다).
  나머지 CC 엣지는 방향이 의미를 갖는다 — 코드근거 `Vinc/api/fragment.py:25`.
  `ATTACHES_TO` 는 노드 타입이 비대칭이라 애초에 역방향이 불가능하다(동 파일 29행).
- ⚠ **문서의 물리 표현이 둘**이다: 구 경로 `Record`–`ATTACHES_TO`–`Concept` 와 현행 D45 경로
  `Chunk`–`MENTIONS`–`Concept`(Chunk 가 원문 정본, "Chunk=SSoT").
  과거 원장 집계가 구 축만 봐서 **개념 74개가 전부 "출처 없음"** 으로 표시된 사고가 있었다
  — 출처확인 `Vinc-docs/vinc/D/vinc.d.atlas-visual-language.md:356` (D54).
- ⚠ **시간이 둘로 갈린다**(D72, 발주자 승인 2026-07-31): 기록 시점(`created_at`)과 **내용
  시점**(`content_time`, 자유 문자열, `YYYY[-MM[-DD]]` 접두 검증 통과분만 저장). 1905년 논문을
  오늘 넣으면 두 값이 다르다. 본문에서 연도를 채굴하는 기능은 **범위 밖**이고 입력은 수동
  필드뿐이다 — 출처확인 `vinc.d.atlas-visual-language.md:362`.

### 어휘 기구 (이미 있음 — GRAPH.md 는 이것과 겹치거나 이어져야 한다)

- 타입은 고정 전역 enum 이 아니라 **주제(theme)별 사용자 저작 어휘**다(D11-R2).
- 어휘 밖 타입은 버려지지 않고 `status:"proposed"` 로 편입되며, 응답의 `proposed_types` 로
  사람의 재가를 요청한다 — 코드근거 `Vinc/api/fragment.py:484`.
- 재가·거부·개명은 **HTTP 전용**이고 **MCP 에 노출하지 않는다** — 코드근거
  `Vinc/api/server.py:655`(ratify) · `:664`(reject) · `:593`(domain rename).
  어시스턴트는 제안만 하고 자기 제안을 스스로 재가할 수 없다. **이 비대칭은 의도된 것이며
  유지해야 한다.**

### 어시스턴트 표면

- **MCP 도구 18종** — 정본 `Vinc/vinc_mcp/tools.py:203` (`TOOLS`).
  주석(readOnly/destructive Hint)은 `Vinc/vinc_mcp/rpc.py:39` (`_tool_specs`)에서 얹는다.
  읽기 12 · 쓰기 6, 쓰기 중 파괴적 4(`vinc_delete` · `vinc_delete_edge` · `vinc_merge_nodes` ·
  `vinc_doc_delete`).
- 쓰기의 주 입구는 `vinc_ingest`(fragment MERGE)와 `vinc_doc_put`.
- 모든 읽기·쓰기는 owner 로 강제 스탬핑된다(SEC-1/SEC-3 — 어시스턴트가 다른 owner 를
  지목해도 그 값은 버려지고 세션 소유자로 대체된다).
- 로컬(stdio)은 **이 기기의 그래프**, 웹 커넥터는 **계정 그래프**에 붙는다. 둘은 자동으로
  같아지지 않는다.

## 조사할 선행 사례

각각에 대해 **무엇을 훔치고 무엇을 버릴지** 판단하라. 실제로 열어 보고 인용할 것.

**에이전트가 읽는 관례 파일**
- CLAUDE.md / AGENTS.md — 사실상 표준이 된 이유, 실패하는 지점(길어지면 무시됨 · 검증 불가 ·
  프로젝트마다 재작성)
- Google Stitch 의 `DESIGN.md` — 이 제안의 직접적 영감. 문서 구성이
  `What is / Import from your codebase / The specification / View, edit, and export /
  Validate with the CLI / Linting rules` 다(출처확인 `https://stitch.withgoogle.com/docs/design-md/overview/`).
  ⚠ 본문이 iframe(`app-companion-*.appspot.com`) 안이라 정적 fetch 로는 안 읽힌다. 실제 브라우저로 열 것.
- llms.txt — 사이트가 LLM 에게 자기를 설명하는 규약
- Cursor rules(`.mdc`) · `.clinerules` · `.windsurfrules` — 규칙 파일의 분할·적용 범위 모델

**그래프 형상을 강제하는 정식 언어** (기계 검증 쪽 끝)
- SHACL / ShEx — RDF 그래프의 형상 제약. **무엇을 검증할 수 있는지의 상한선**을 여기서 잡아라
- OWL / schema.org / JSON-LD — 어휘 정의와 상속
- Neo4j·Datomic 의 스키마-온-리드 vs 온-라이트 논쟁

**지식 관리 관례** (사람 쪽 끝)
- Zettelkasten 의 원자성(atomicity) — "개념 하나의 크기"에 대한 가장 오래된 답
- Obsidian·Roam 커뮤니티의 명명·링크 관례가 어떻게 수렴/발산했는지

**MCP 자체**
- `resources` · `prompts` 프리미티브 — 서버가 클라이언트에 문서를 **자동으로** 내려줄 수 있는
  규격. GRAPH.md 를 사람이 "읽어라"라고 시키지 않아도 되게 만드는 경로.
  실제 호스트들이 이걸 얼마나 지원하는지 **실측**할 것(Claude Desktop·Claude Code·Cursor·
  ChatGPT 각각). 지원이 고르지 않다면 그 사실이 Q4 의 답을 바꾼다.

## 답해야 할 질문

**Q1. 무엇이 들어가야 하는가?**
최소 절 집합을 제안하라. 각 절에 **"없으면 실제로 무엇이 망가지는지"** 를 한 줄로 붙일 것.
근거 없는 절은 넣지 마라. 가설(검증·반박할 것): 도메인 표기 · 노드 종류 판별 · 관계 어휘와
방향 · **입도** · 금지 목록 · 문서 규약(위 두 물리 경로 중 무엇을 쓸지, `content_time` 을
언제 채울지).

**Q2. 입도(granularity)를 어떻게 글로 적을 수 있는가?**
이것이 나쁜 그래프의 최대 원인이라고 본다(이 가정부터 검증하라). "개념 하나 = ?" 를 LLM 이
일관되게 따를 수 있는 형태로 쓴 선행 사례가 있는가? **규칙으로 쓰는 게 나은가, 3~5개의
양·음성 예시로 보이는 게 나은가?** 근거를 대라.

**Q3. 어디까지 기계로 검증할 수 있는가?** (작업량을 가르는 질문 1)
GRAPH.md 를 사람이 읽는 산문과 기계가 읽는 블록으로 나눠야 하는가?
Vinc 에는 이미 재가된 타입 어휘가 **스토어 안에** 있다 — GRAPH.md 의 관계 절을 거기서
**생성**하고 **대조**하는 것이 가능한가? 그렇다면 **문서와 스토어 중 무엇이 정본인가?**
(둘 다 정본이면 반드시 어긋난다. 이 답이 GM-3 을 결정한다.)

**Q4. 어디에 두고 어떻게 읽히는가?** (작업량을 가르는 질문 2)
- (a) 사용자 리포의 파일 — 코드 0, 오늘 됨. 어시스턴트가 읽으라고 시켜야 함. 계정 그래프엔 안 따라감
- (b) 그래프 안의 문서(`doc_id: graph.md`) — 팩·동기화에 함께 이동. 여전히 "가져와라"가 필요
- (c) MCP resource 로 노출 — 호스트가 자동 수령. 규격은 있으나 지원이 고르지 않음(실측할 것)

각각의 실패 모드를 적고 **단계적 경로**를 권고하라.

**Q5. 어떻게 만들게 하는가?**
현행 도구(`vinc_domains` · `vinc_diagnose` · 타입 census)만으로 기존 그래프에서 초안을
뽑아낼 수 있는가? 뽑아낸 초안이 쓸 만하려면 무엇이 더 필요한가? Stitch 의 "Import from
your codebase" 에 대응하는 것이 Vinc 에서는 무엇인가?

**Q6. 어떻게 실패하는가? (반증 — 필수)**
이 제안이 나쁜 아이디어일 경우를 진지하게 논하라. 후보:
- 아무도 안 쓴다(관례 파일의 일반적 운명)
- 길어져서 컨텍스트만 먹고 무시된다
- 스토어의 어휘와 어긋나 **거짓말하는 문서**가 된다
- 어시스턴트의 판단을 과하게 묶어, "의미 판단은 어시스턴트가 한다"는 **원칙 자체를 무력화**한다

각각에 대해 **관측 가능한 조기 신호**와 완화책을 제시하라.

4. **Q1~Q6 각각에 대한 근거 있는 답.** 주장마다 근거 라벨을 붙일 것.
5. **반대 의견** — 이 설계를 반대할 가장 강한 논거와, 그럼에도 진행한다면 그 이유.
6. **미해결** — 연구로 답이 안 나온 것과, 그것을 답하려면 무엇을 실측해야 하는지.

## 하지 말 것

- Vinc 에 없는 기능을 전제하지 마라(위 `확정 사실` 이 현행이다).
- "AI 가 알아서 잘할 것" 으로 넘어가지 마라 — **그 가정이 지금 문제의 원인이다.**
- 예시 프롬프트 모음을 만들지 마라. 원하는 산출물은 **문서 규격**이다.
- 형식 언어(SHACL 등)를 그대로 채택하자고 하지 마라. 조사는 하되, **사람이 읽고 LLM 이
  따르는 마크다운**이라는 제약을 지켜라.
- 화면 노출 텍스트에 em-dash(`—`)를 쓰지 마라(D38). 이 문서 자체는 내부 문서라 무관하나,
  예시 GRAPH.md 가 제품 UI 에 실릴 가능성이 있으면 지킬 것.
