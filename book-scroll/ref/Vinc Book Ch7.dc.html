Vinc Book Part 0, Chapter 7

Chapter 7

The Being That Uses Memory

But memory does not act by itself.

Something has to read it, compare it with the present, find what matters, and create new judgments when necessary.

Memory needs a user.

We call that user an Agent.

7.1

An Agent Changes According to What It Reads

Even with the same model, behavior changes according to what the model is allowed to read.

An Agent that sees only the current question and an Agent that also sees past decisions and failures will approach the same problem differently.

An agent is what it reads.

7.2

Giving Memory to an Agent

Giving an LLM a graph-search tool does not by itself create an Agent with memory.

If an Agent reads the current situation, finds related Concepts, checks past Decisions, avoids previously failed approaches, and proposes new memory when necessary, the graph becomes more than a knowledge base.

It becomes the Agent's working context.

7.3

An Agent Can Also Be a Node in the Graph

If we think of an Agent only as a prompt or code bundle, changing roles or connecting multiple Agents becomes difficult.

So in Vinc, a Role can be treated as a node.

The Agent is not merely an executor. It becomes a graph node with a contract.

7.4

But an Agent Node Is Not a Static Manual

Real work keeps changing.

A role may begin simply and then encounter a new problem. Another Agent may deliver new information. The Agent may discover its own failure. A person may change a priority.

Node identity and node content are not the same thing.

7.5

Communication Between Agents Becomes Memory

A Design Agent may discover a constraint during implementation. Passing that fact to an Implementation Agent changes the conditions of the next task.

The important thing is not the conversation itself, but how the graph's meaning changes because of the conversation.

One Agent's experience becomes another Agent's memory.

7.6

Workflow Is Also a Relationship

When several Agents work together, an order naturally appears.

This order could be hard-coded in orchestration code. But when represented in the graph, the relationship between Agents becomes memory itself.

Workflow is also a relationship.

7.7

One Failure Becomes Memory for the Next Task

An Agent can make a mistake. What matters is that the failure does not disappear into a log.

If its cause is understood and preserved as memory applicable to a role or task, the next Agent can read it.

One failure can become a constraint on the next task.

7.8

Controlling an Agent Is Not the Same as Trusting It

Recording a role and its rules in the graph does not mean the graph physically enforces every behavior.

Vinc is therefore neither merely a scheduler nor an executor. It is a memory structure that describes the context in which an Agent should act.

Providing memory and enforcing action are different problems.

7.9

When Memory Changes, the Agent Changes

The initial Agent has limited information. As work proceeds, it learns Concepts, forms relationships with other Agents, experiences failures, and receives new judgments from people.

These values change over time. But the change should not be arbitrary overwriting.

We should be able to trace what changed and why.

7.10

The Agent Is Both User and Producer of Memory

At first, the Agent appears to be something that takes memory from the graph. But the flow also goes in the opposite direction.

The Agent reads memory, makes judgments, performs work, and produces new facts, failures, and decisions. Those are then recorded back into the graph.

The Agent is both a user of memory and a producer of new memory.

If an Agent reads memory and acts on it, what happens when that memory is wrong?

Once we give an Agent memory, we have to ask whether that memory deserves to be trusted.
