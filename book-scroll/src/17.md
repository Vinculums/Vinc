# How Meaning Becomes Space

Vectors are one of the least visible parts of a memory system. A graph has nodes and relationships. A document has text a person can read. A vector, by contrast, is just an array of numbers. But in a retrieval system, that array of numbers does something important: it places a piece of text into a semantic space.

In VINC, the pipeline for producing a vector is simple.

```text
Document → Chunk → embed → vector store
```

A whole document doesn't get turned into a vector all at once. It's first split into small Chunks, which become the smallest unit of retrieval. Each Chunk is then fed into an embedding model, and the resulting vector gets stored.

What matters here isn't the vector itself so much as which space it was placed into.

## Chunks Have to Exist First

Embedding doesn't happen out of nowhere — there has to be text to embed in the first place.

```text
Document
 ├─ Chunk 1
 ├─ Chunk 2
 ├─ Chunk 3
 └─ Chunk 4
```

Each Chunk becomes an independent retrieval target. So the size and boundaries of a Chunk directly affect retrieval quality.

A Chunk that's too large mixes unrelated content into a single vector. One that's too small loses its context. So retrieval quality isn't decided by the embedding model alone — what gets packed into a Chunk matters just as much.

## Embedding Is a Transformation into Semantic Space

An embedding model turns text into a fixed-dimensional array of numbers. If a model outputs 768 dimensions, a Chunk gets represented as 768 real numbers.

At search time, the query gets turned into a vector the same way, and the system computes similarity between the stored vectors and the query vector.

That's what makes vector search different from plain string matching — two pieces of text don't have to share the same wording to become candidates, as long as they sit close together in semantic space.

## Vector Dimension Is Part of the Storage Contract

A real technical problem shows up here. If a vector store expects 768-dimensional vectors and a new embedding model produces vectors of a different size, swapping the model alone doesn't finish the job. The storage structure has to be compatible with the model's output space too.

The embedding model, the vector dimension, and the vector store are bound together in a single contract. That's why changing the embedding model isn't a simple configuration change. If existing data lives in the semantic space of the old model, it has to be transformed again to fit the search space the new model defines.

Changing models can pull in the following chain:

```text
Model change
    ↓
check dimension / space
    ↓
check existing vector compatibility
    ↓
re-embed
    ↓
rebuild index
```

Changing the storage structure alone doesn't magically move existing vectors into the new semantic space.

## A Vector Is Not Memory Itself

A successful vector search doesn't mean memory has been reconstructed. A vector doesn't stand in for the original text, and it doesn't stand in for the graph's concepts or relationships either.

A single search result can involve at least three different kinds of information: the original text, the vector, and related graph Nodes. The vector is the retrieval representation among these. The original text provides evidence, the graph provides meaning and relationships, and the vector is used to find candidates that are close in meaning.

Treating a vector as identical to memory misunderstands what a retrieval system is for.

## Retrieval Quality Isn't Decided by the Model Alone

Change how documents get chunked, and retrieval results can shift even with the same embedding model. Change the model, and the semantic space shifts even with the same Chunks. Keep the same vectors, and the final outcome can still change depending on which candidates get chosen after retrieval.

Embedding, then, is one stage of the retrieval pipeline — not the whole retrieval system.

## The Cost of Changing a Model

Replacing an embedding model doesn't just cost processing time. Existing Chunks have to be re-embedded, new vectors have to be stored, and search indexes have to be rebuilt. This cost grows as data grows, and if the model's dimension changes too, storage compatibility becomes another thing to check.

This isn't a model-selection problem — it's a retrieval-infrastructure problem. This cost gets revisited with real numbers later, in Part 4.

## The Boundary Between Vectors and Meaning

A vector doesn't directly explain meaning. Two pieces of text having a short distance between their vectors means they're close in the embedding model's semantic space — it doesn't mean they're the same memory.

So in VINC's retrieval structure, vector search is used to generate candidates, but final identity is never left to vector similarity alone. That distinction is exactly what makes the resolution step in the next chapter necessary.

A vector isn't the final form memory takes. It's a coordinate for finding memory.
