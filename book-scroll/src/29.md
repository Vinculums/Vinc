# A Tool's Efficiency Is Measured in Calls

## Transport Latency Alone Isn't Enough

The easiest thing to measure first, when evaluating an MCP tool, is call latency.

But from an Agent's perspective, what matters isn't how many milliseconds a single call takes. The more direct cost is how many calls the Agent needs to resolve one question.

Consider these two paths:

```text
question
→ search
→ check node
→ check relation
→ check record
→ inspect again
→ answer
```

versus a tool built like this instead:

```text
question
→ return the needed node + evidence + relation together
→ answer
```

Even if every individual MCP call runs at the same speed in both systems, the total cost of solving the task differs enormously. So VINC's MCP efficiency evaluation treats calls-to-resolution as its core metric.

## What Counts as Resolution

Counting calls alone isn't enough either. A single call that finds nothing has a low call count without being efficient.

So call efficiency has to be viewed across at least these axes together:

| Metric | Meaning |
|---|---|
| Task Success | did it actually solve the task |
| MCP Call Count | how many calls it took to resolve |
| Unnecessary Call Rate | how many calls contributed nothing to the result |
| Payload / Token Volume | how large a result the model had to process |
| Evidence Resolution | did the answer actually reach its supporting evidence |
| Recovery | did it recover from a wrong search or an empty result |

In this framing, "a fast API" isn't automatically a good tool. A good tool returns accurate material in few calls, and doesn't force the Agent to go exploring again afterward.

## Where the Bottleneck Showed Up in VINC

Evaluation based on real MCP interaction found that a single retrieval's responsiveness, and traversal from a concept to its neighborhood, were both observed at a comfortably practical level.

Repeated sequential calls, though, exposed round-trip cost. As result payloads grew, the bottleneck shifted from the transport layer toward the model's context window.

This observation points somewhere important:

«MCP's next optimization target doesn't have to be transport latency.»

Compressing several stages of calls — search, check, check relation, check again — into one meaningful retrieval shape can have a much bigger effect.

## Search and Brief Don't Compete

Given this, search and the material-assembly tool (brief) shouldn't be read as two competing search tools.

Search is closer to a primitive that finds candidates. Brief is closer to a composite retrieval: it takes a question, searches, resolves a target, and combines that Node's context.

Structurally:

```text
Search
    ↓
candidate retrieval

Brief
    ↓
search
    ↓
resolution
    ↓
node context
    ↓
answer material
```

So the thing worth evaluating isn't which tool is faster. It's how the entire call path needed to solve the same task changes.
