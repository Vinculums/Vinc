# How Search Results Get Confirmed as Memory

Search is the entrance to a memory system. But a search result isn't memory by itself.

A single question can surface several candidates.

```text
Question
   ↓
Search
   ↓
Candidate A
Candidate B
Candidate C
```

The problem isn't finding a lot of candidates. It's deciding which one should actually be interpreted.

## Candidates Arrive Through Different Paths

Search candidates don't all come from one database.

A text search result can be a candidate. A vector search result can be a candidate. A graph Node can be found directly, through a title that shares words with the question, or because a top-ranked chunk mentions it. Other stored objects like Records or Decisions can connect to a question too.

What matters is that these candidates aren't all the same shape. A search result can be a document Chunk. A graph result can be a Concept. A Record is a distinct kind of recorded object.

## Candidate and Resolution Are Different States

Chapter 16 already showed that this system doesn't pick when things are ambiguous. The question here is how that principle actually gets enforced.

```text
Search
  ↓
Candidates
  ↓
Resolution
  ↓
One Node
```

If two candidates look equally plausible, the point isn't that some rule has to justify picking one of them — the absence of any basis for picking is itself a valid outcome. Picking the wrong Node drags everything explored afterward in the wrong direction, which is exactly why not picking counts as a normal response from the system, not a failure.

Understanding resolution as a simple similarity threshold misses this structure. Search is the stage that produces candidates. Resolution is the stage that checks whether one of them can actually be identified.

```text
Search = what could be relevant?
Resolution = which of these is it pointing at?
```

This split lets a search system stay broad while retrieval, and stay conservative at the resolution step.

## The Pool Is the Ceiling

Resolution can only choose among candidates that entered the pool. A ranking change, however clever, reorders the pool; it cannot reach a Node that was never in it.

That is not a hypothetical. Measured on one store in September 2026, most of the Nodes a question set was about never became candidates at all, and deepening the pool four times barely moved that. What moved it was candidacy: which kinds can be named, and how a title is matched. Ranking came after, and had to.

## Material Gets Pulled From the Resolved Node

Once one Node is resolved, the system can start assembling material around it.

```text
resolved Node
      ↓
related Concepts
related Records
related Decisions
      ↓
documents / excerpts
      ↓
answer material
```

The graph matters here. If a search result lands on a particular Concept, the Records and relationships connected to that Concept can be explored. Chunks from related documents can also serve as evidence.

A search result stops being just a list of text and becomes the starting point for further navigation.

## A Record Is a Different Kind of Object Than a Concept

A Concept is a unit of meaning the system works with. A Record is an object that preserves a specific fact or observation.

```text
Concept
   │
   └── ATTACHES_TO
          │
        Record
```

A search result landing on a Concept doesn't mean its attached records should automatically be treated as identical to it. Nor does a Record being found make it the same as the concept it describes. After resolution, these different objects still have to be read as connected but distinct.

## Episodes Are Candidates Too, and Name a Different Thing

An Episode records something that happened, in chronological order. For a long time it could not be named by retrieval at all: the candidate pool was built from Concepts, Records and Decisions, and a store's Episodes, however many, could never enter it. That was measured in September 2026 and closed the same day. An Episode is now a candidate like the other three.

What it names is different. A Concept answers what something means; an Episode answers what happened and when. So when a question asks about an event, the Episode is the target, and once resolved it comes with its relations like any other Node.

```text
Question
   ↓
resolved Episode
   ↓
its relations
   ↓
temporal context
```

One thing stays out of the searching surface: the Episode's narrative summary. Read for matching, a summary is wide enough to win questions that have no answer in the graph, so it stays in the answer material and out of the search.

## Language Differences Are Also a Post-Search Problem

The same concept can be expressed in different languages. A Korean question can point at a Concept or Record written in English. Plain string matching isn't enough here.

Embedding closes that gap for the text. For naming a Node it does not, and this was measured: candidacy follows how many of a title's words the question carries, and the semantic arm reorders chunks without putting a title on the candidate list. So language differences get handled by broadening the text candidates at the search stage, and by confirming identity through structure at the resolution stage. A title in another language that never enters the pool is a candidacy problem, not a ranking one.

## Search Failure Is Also a Valid State

Sometimes there's no result. Sometimes there aren't enough candidates. Sometimes the candidates can't be told apart.

In these cases, the system doesn't force a memory into existence.

```text
no candidate → no resolution
ambiguous candidates → no resolution
```

This isn't a failed search — it's an important system state. One of the most dangerous outcomes in a memory system is resolving a target with no basis for it, and letting every downstream step treat that target as fact.

So VINC's retrieval structure needs both the ability to find, and the ability not to choose.
