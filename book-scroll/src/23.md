# What Time Exists in Memory

Time isn't singular in memory.

When an event described by a record actually happened, and when that record entered the Graph, are two different questions. VINC splits these into world time and graph time.

## World Time

World time belongs to whatever memory is describing. When a Concept or Record describes an event or fact, content_time can express when that referent occurred.

```text
Record
  content_time = 2026-08-20
```

That value can differ from when the Record was actually stored in the Graph.

## Graph Time

Graph time describes when an object was created or changed inside the Graph itself. Concepts and Records carry graph-state fields like created, updated_at, rev, sync_seq.

```text
World time
    ↓
what happened

Graph time
    ↓
when the graph knew about it or changed it
```

Neither can substitute for the other.

## Mixing the Two Clocks Causes Errors

Say an event happened on August 20 and got recorded on September 1.

```text
Event
content_time = Aug 20

Record
created = Sep 1
```

A Record being recently created doesn't mean the event happened on September 1. Likewise, an old event's record being edited recently doesn't mean the event happened again.

## Records Can Also Have a Validity Window

If content_time marks when an event occurred, valid_from and valid_until mark when the claim itself was valid.

Pricing or policy information, for instance, can be true at one point and no longer true now. In cases like that, the event's timing has to stay separate from the claim's validity window.

## Decisions Can't Be Handled the Same Way

Unlike a typical Concept or Record, a Decision doesn't carry content_time. Its important temporal information is when it was created and tracked in the graph — because a Decision represents a judgment made inside the system, rather than describing an external event.

So different object kinds need different temporal models, and that has to be accepted rather than flattened away.

## Episodes Have Yet Another Temporal Structure

An Episode exists to recall what happened, in chronological order. So its core property is its position on a timeline.

Applying the graph's creation-time model straight onto an Episode can blur its meaning. Which is why forcing the same time fields onto every Node kind, uniformly, isn't the right design.

## Causal Time Is a Different Problem Entirely

Two events sitting in chronological order doesn't prove one caused the other.

```text
A happened before B
```

and

```text
A caused B
```

are different claims.

Relations like prerequisite_of, derives_from, and inherits_from carry a structural meaning stronger than a simple date comparison.

```text
A ──prerequisite_of──> B
```

This doesn't just mean A's date comes earlier than B's. It means A has to come first for B to be understood or to hold at all.

## A Causal Cone Spatializes Time

Apply causal relationships to the Graph, and you can explore, from a given Node, both what influenced it and what it influences.

```text
        upstream
           ↑
           │
      ┌────A────┐
      │    │    │
      B    C    D
           │
           ↓
        downstream
```

This isn't a third clock. It's time and causal relationships expressed as two different structures within the graph.

## Time Is Not a Viewpoint

VINC's View design doesn't treat time as a separate viewpoint — it treats it as a state axis shared across 3D and 2D.

```text
Viewpoint
= how it's being viewed

Time
= which temporal state is being viewed
```

Blur these two together, and the View model gets needlessly complicated. Time isn't a matter of swapping camera or renderer — it constrains the state of the data itself.
