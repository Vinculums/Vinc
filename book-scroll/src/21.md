# A Role Is a Node

Treat an Agent as just a program, and it becomes hard to say what memory that Agent is even supposed to use.

Agents sharing the same Graph can have entirely different purposes. One Agent handles retrieval, another handles evaluation, another analyzes documents.

VINC expresses this difference as an Agent Role. And a Role isn't just a configuration value — it can be a Node that persists and gets referenced inside the Graph.

## Representing an Agent as a Concept

An Agent can exist in the Graph as something like `concept:agent-*`.

```text
Agent
  ├─ Role
  ├─ Domain
  ├─ Decisions
  ├─ related Concepts
  └─ Prompt surface
```

With this structure, an Agent's role can be explored the same way any other concept in the Graph is. Representing an Agent as a Graph Node separates its definition from its execution process.

## A Role Describes the Boundary of Behavior

An Agent Role isn't just a label.

Say a particular Agent handles retrieval. What kind of information should it look for, which Domain does it operate in, which Prompts can it use — all of this can be expressed as connections.

```text
Agent Role
   ├─ identity
   ├─ purpose
   ├─ domain
   ├─ constraints
   └─ related Decisions
```

This way, an Agent's behavior doesn't have to get crammed into one giant system prompt.

## Separating Agent From Prompt

MCP can expose an Agent Role's list and contract externally through a Prompt surface. Agent and Prompt shouldn't be treated as the same thing here.

Agent expresses who performs a role. Prompt expresses what instructions carry out that role.

```text
Agent
  ↓
Role
  ↓
Prompt
  ↓
tool use
  ↓
memory
```

With this structure, the Prompt an Agent uses can be swapped, or the Prompt surface expanded, while the Agent's own identity in the graph stays intact.

## The Graph Is Not the Scheduler Directing Agents

Representing an Agent as a Graph Node doesn't turn the Graph into something that directs how an Agent runs.

The Graph can express things like this:

```text
Agent A
  ├─ uses → Concept X
  ├─ relates → Decision Y
  └─ follows → Prompt Z
```

But when it runs, how many times, and which worker runs it — those are the runtime environment's job, not the Graph's.

```text
Graph = the Agent's meaning and relationships
Runtime = the Agent's actual execution
```

This separation matters a lot. Start using the Graph as a scheduler, and semantic structure and execution state end up tangled into one thing.

## An Agent Is Both a User of Memory and Part of It

Up to now, an Agent has just been described as something that uses memory. Model it as a Graph Node, and it goes one step further — the Agent itself becomes something referenceable inside the Graph.

Which Agent Role produced a particular Decision, which Agent works with a particular Concept, which Prompt connects to a particular role — all of this can be expressed in the Graph. That turns an Agent from a one-off execution object into a persistent, referenceable component of the system.

## A Role Can Outlive Its Implementation

An Agent's implementation can change without necessarily changing what its Role means. The model or the tool-calling mechanism behind a retrieval role, for instance, can change while the retrieval role itself stays the same.

Separating Role from implementation lets system changes get managed in smaller pieces. The Graph expresses meaning that persists; the runtime expresses however execution happens right now.

## Roles Together Form a Roster

Model Agent Roles as Concept Nodes, and the system can build an Agent roster directly out of the Graph.

```text
Agent roster
 ├─ retrieval Agent
 ├─ evaluation Agent
 ├─ documentation Agent
 └─ analysis Agent
```

Each Agent carries its own Domain and relationships. This is more powerful than a flat list, because Agents can be explored the same way any other graph element is — which Domain an Agent belongs to, which Concepts it touches, which Decisions it references, all confirmable within a single Graph.

## Why Turn Roles Into Nodes

The point of turning Agent Roles into Nodes, in the end, isn't to make Agents more complicated. It's to let the system describe its own execution structure.

In this structure, an Agent is both something external that uses the Graph, and something the Graph can, in turn, describe. The role that uses memory becomes a structure the memory system itself can understand.
