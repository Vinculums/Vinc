# How Memory Leaves the System

A memory system can work perfectly well internally and still have limited practical value if an Agent can't reach it.

VINC connects this boundary through MCP, the Model Context Protocol.

```text
Agent / Host
      ↓
MCP
      ↓
VINC's dispatcher
      ↓
VINC's tools
      ↓
Graph / Document / Search
```

The MCP layer doesn't decide the meaning of memory here. It's the boundary that carries an external system's request into VINC's internal functionality.

## A Thin Bridge

VINC's MCP implementation is kept as thin as it reasonably can be. What this layer handles is protocol processing, request validation, authentication, choosing which space to access, dispatching tool calls, and limiting result size.

What it deliberately doesn't handle matters just as much. Semantic judgment, concept structuring, deduplication, deciding what memory means — none of that happens here. That responsibility stays inside VINC's search, graph, and document layers.

The reason is simple. Let this boundary start making judgment calls, and the door itself becomes a second implementation of the graph's contract. Changes to the door and changes to the graph's rules need to be free to happen at different speeds.

## Two Channels, One Dispatcher

VINC can be reached through a local channel (stdio) or a remote channel (HTTP). Whichever channel is used, requests pass through the same dispatcher internally. So requests like "initialize," "ping," "list tools," and "call tool" all go through one shared processing structure.

The core idea here is keeping the channel separate from memory's logic.

## MCP Is VINC's Boundary, Not VINC Itself

From the outside, VINC can look like a collection of tools. Internally, though, this boundary doesn't define the whole memory system.

```text
MCP
 ↓
tool surface
 ↓
VINC's internal system
```

MCP is the protocol boundary through which an external Agent reaches VINC. Change this boundary, and the underlying structure of the Graph, Document, and Retrieval layers doesn't necessarily have to change with it. That separation is what gives the system room to grow over the long run.

## Tools Carry a Safety Boundary, Not Just a Function

Not every VINC tool carries the same risk. Reading is different from writing; deleting a document is different from searching one.

VINC derives a tier for each tool from its annotations and registration metadata, and manages safety according to that tier.

```text
tool
 ↓
annotation
 ↓
tier
 ↓
allowed operation
```

The important principle here: when in doubt, default to blocking. When a tool's safety characteristics can't be confidently determined, the more dangerous permission never gets granted automatically.

## Authentication and Space Are Managed Together

Authentication alone isn't enough when an external system uses VINC. Which graph space it's accessing has to be settled too. A team route creates a boundary like this:

```text
/t/<team-uuid>/mcp
          ↓
       team space
```

Even an authenticated request shouldn't be able to reach data outside the correct space. Every request gets checked for authentication and space selection before a tool actually runs. That's what keeps the access-control principle stable regardless of which channel the connection came through.

## Results Need a Boundary Too

Search results and assembled material can grow as connected memory grows. These results eventually flow into an Agent's context. Without a size limit, more accurate retrieval still means more call cost and more processing on the Agent's side.

So VINC's MCP surface has a result budget. Search and material-building tools can carry a mechanism that shrinks oversized results. What matters isn't cutting data arbitrarily — it's understanding the shape of the result and narrowing it while keeping what's needed. When a result has to be narrowed so far that the original can't be handed back intact, the fact that it was narrowed becomes a signal in itself.

## Call Count Is Also Part of the Design

Say an Agent uses memory by repeatedly searching, inspecting, checking a relationship, inspecting again, searching again. Each individual call can be fast, but solving the whole problem still takes multiple round trips.

Compress the necessary exploration into a single higher-level surface instead, and a single question can return a resolved Node, its context, and its evidence all at once.

So MCP's performance can't be judged by channel response time alone. From an Agent's point of view, what matters more is how few calls it took to reach an answer, how many of those calls turned out unnecessary, whether result size stayed reasonable, and whether evidence actually got secured. This question comes back with real numbers in Part 4.

## What This Boundary Doesn't Do

MCP doesn't solve every problem a memory system has. Changing the vocabulary itself — deciding what counts as a particular kind of Concept — isn't this boundary's responsibility. Keeping that line intact is what keeps the MCP layer from accumulating more responsibility than it should carry.

MCP's role, in the end, is simple: let an external Agent invoke VINC's memory functions safely and consistently. The actual meaning of memory, above that, belongs to the Graph, the Document, Retrieval, and Resolution.
