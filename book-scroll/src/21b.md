# How a Role Becomes a Contract

Chapter 21 turned an Agent into a Node on the graph. We saw a search Agent and an evaluation Agent each get their own identity, separate from execution.

Identity alone isn't enough, though. Labeling an Agent "handles search" is different from actually pinning down what it has to read and what it can't do. A name only points at a role — it doesn't say what the role demands.

## Mission Comes First

A Role Node needs a Mission describing what that role is supposed to do. Two Agents reading the same repository can still need to behave completely differently if their purposes differ.

```text
Development Agent
    → implements, changes contracts

Verification Agent
    → confirms the change satisfies requirements
```

This isn't just a difference in wording. One has authority to change something; the other must not change anything, only verify. That distinction has to survive in the graph as a Mission, so later on, you can trace back why an Agent acted (or didn't act) the way it did.

## Reading Order Is Part of the Contract Too

Having access to a lot of material doesn't mean it's fine to read it in any order. Some roles have a document to check first, a relationship to look at next, and a condition to verify last.

```text
question
  ↓
role-defined order
  ↓
read this first → then check this → verify this last
  ↓
act
```

Pin the reading order down as part of the role, and different Agents looking at the same graph can follow genuinely different exploration paths.

## A Door That Has to Be Passed

Finishing a task doesn't automatically mean the task is done. Each role can have a Gate — a condition that has to pass before work moves to the next stage.

```text
work done
  ↓
Gate
  ├─ pass → next stage
  └─ fail → stays, or gets revised
```

Without this door, "I did the work" and "the work is actually finished" become indistinguishable.

## Several Roles Chained Together Become a Flow

Real work rarely finishes inside one role. It moves through stages — research, design, implementation, review, release. If each stage has a responsible role, that sequence itself can be expressed as a graph relationship.

```text
research
   ↓
design
   ↓
implementation
   ↓
review
   ↓
release
```

This arrow isn't just "whose turn is next." It captures the fact that a later stage depends on an earlier one.

What matters here: writing this flow into the graph doesn't mean the graph enforces and executes that order. The graph only describes who's responsible for what, and how those responsibilities chain together. When it actually runs, how many times, and which worker handles it — that stays the job of a separate runtime.

## Three Actions Keep the Contract Honest

There's a gap between a role existing in the graph and a runtime actually acting according to that role. Closing that gap takes at least three actions:

- read the role from the graph
- turn what was read into something the runtime can use
- check that what got generated still says the same thing the graph's original does

Keep these three separate, and the graph stays the source of truth for a role, while whatever gets generated in the runtime is a derived artifact.

## A Role Has to Be Visible From Outside Too

A role that only exists inside the graph never reaches the external system that's supposed to carry it out. So a role's contract has to be exposed in a form outside systems can query.

One principle matters here: this externally exposed copy can't turn into a separately, manually maintained document. When the role changes in the graph, the contract visible outside has to change with it.

## A Role Needs a Fence

Give an Agent unrestricted access to every piece of material, and the boundary that originally defined its role stops meaning anything.

```text
role
  ↓
only material within the allowed scope
  ↓
readable memory
```

This fence isn't only about security. Letting an Agent read unrelated material unnecessarily widens what it has to judge — and that blurs the role itself.

## The Graph Is a Contract, Not a Conductor

Putting a role into the graph isn't about making the graph conduct execution.

```text
Graph = preserves the role's contract
Runtime = actually acts according to that contract
A person or automated check = confirms whether it's okay to move to the next stage
```

Keeping this split lets changing a role's definition and changing the infrastructure that executes it move at different speeds, independently.

In the end, having many Agent Roles isn't what matters. What matters is that each role's responsibility, reading order, required gates, and prohibitions stay traceable inside the graph.

Chapter 21 covered what a role exists as. This chapter covered what that existence actually holds it to. What's left is the relationships this role produces — and the evidence attached to each one.
