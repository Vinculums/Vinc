# Failures That Look Like Success

## Getting a Number Isn't the Same as Success

The most dangerous failure in system evaluation isn't the obvious kind. What's more dangerous is running the wrong experiment while returning perfectly normal-looking numbers.

Say you're evaluating cross-lingual retrieval, but the actual fixture has zero cross-lingual pairs in it. The benchmark can still run. The metric still gets computed. But that number isn't measuring cross-lingual retrieval performance at all.

This is a failure that looks like success.

## A Failed Vector Arm Produces the Same Problem

Some of VINC's evaluations hit timeouts on the vector retrieval arm. If the resulting system just returned text-search results in that case, the search can look, from the outside, like it succeeded. But if the thing being evaluated is hybrid retrieval, that's not success.

So a result needs to record, alongside the plain search result, which retrieval arm actually ran. Only once each path's execution is confirmed can the final result be interpreted correctly.

## Empty Retrieval Is Also Information

An empty search result doesn't automatically mean the system failed. The question might genuinely have asked for something that doesn't exist.

The bigger problem is when a search comes back empty and the Agent picks some other Node arbitrarily instead. This is exactly where VINC's resolution principle matters:

«When it's ambiguous, don't pick.»

If a search doesn't return enough, keep the result empty as-is, and recover through a different path if one exists. That's how false positives get reduced.

## Recovery Gets Measured

So evaluation has to include what happens after a failure, too.

```text
Query
 ↓
Retrieval
 ↓
Empty / Wrong
 ↓
Recovery
 ↓
Resolution
```

Record whether recovery succeeded, how many extra calls it took, and whether evidence was finally secured. Only then can "succeeded on the first try" be told apart from "succeeded after five wrong turns."
