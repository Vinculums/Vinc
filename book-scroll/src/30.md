# How Embedding Models Get Compared

## A Model Isn't a Single Number

Swapping an embedding model doesn't just change vector quality. An embedding model defines the retrieval system's entire semantic space.

So a model change needs at least these four things evaluated together:

```text
retrieval quality + compute cost + storage structure + operational cost
```

Pick a model on retrieval quality alone, and unexpected costs can show up in the real system later.

## Compare Under the Same Conditions

VINC's embedding evaluation compares different models under identical evaluation conditions. What matters more than absolute scores is the relative difference between models within the same fixture.

Language characteristics matter especially for Korean retrieval. One experiment observed Korean nDCG dropping as low as 0.472 from 0.670. That gap isn't just a difference in model name — it shows how well a semantic space actually fits that retrieval workload.

## Quantization Is Part of the Model

Running an embedding model as int8 doesn't automatically get you the same performance characteristics every time. A quantized model has to be evaluated alongside what the execution kernel actually supports.

One int8 evaluation, for instance, assumed a particular CPU instruction extension. When the runtime environment doesn't match that kernel assumption, accumulator behavior and performance characteristics can shift.

So these two need to stay separate:

```text
Model capability ≠ Runtime capability
```

A model supporting int8 doesn't by itself guarantee that a given system gets the int8 performance it's hoping for.

## Record Retrieval Quality Together With Runtime Conditions

An embedding evaluation's result needs to preserve, at minimum:

```text
Model, Dimension, Precision, Quantization, Kernel,
Corpus, Query set, Language, Metric, Latency, Result
```

Without this, the result can't be reinterpreted later. So an embedding benchmark shouldn't be a model leaderboard — it should be a record of system conditions.
